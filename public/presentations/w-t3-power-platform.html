Why it matters

Low-code is still code

Choosing the app type

Canvas, model-driven or Code App? The right choice up front saves a rebuild later.

Module 1, about 15 minutes. The most expensive mistake in Power Platform is picking the wrong app type and rebuilding six months later.

Module 1 · Decision

Canvas vs model-driven vs Code Apps

CanvasModel-drivenCode App
Built withPower Fx in StudioConfiguration over DataverseReact / Vue + TypeScript in your IDE
UI controlPixel-levelStandard forms and viewsTotal — any npm library
DataAny connectorDataverse onlyDataverse and connectors from code
Best forTask apps, mobile, field workCase and record management, back officeComplex UI and logic, pro-dev teams

Source controlVia solutionsVia solutionsNative Git

Rule of thumb: data-heavy back office → model-driven. Task-focused or mobile → canvas. Outgrowing Power Fx, or you have React developers → Code App.

Walk the table row by row. The key trade-off is control versus speed: model-driven is fastest for data-centric apps, Code Apps give total control but need developers.

Mixing is normal: a model-driven back office for staff plus a canvas or Code App for a focused task. Licensing changes regularly, so always check the current licensing guide before committing.

02

Canvas apps done properly

Declarative Power Fx, reusable components, delegation and performance.

Module 2, about 35 minutes. Most people learned canvas apps by putting everything in OnStart and OnSelect. Modern Power Fx gives us better tools.

Module 2 · Power Fx

Named formulas replace OnStart

App.Formulas
// Declared once, evaluated when first used, always up to date
CurrentUserEmail = User().Email;

OpenReferrals =
    Filter(Referrals, Status = 'Status (Referrals)'.Open);

UrgentCount =
    CountRows(Filter(OpenReferrals, Priority = 'Priority'.Urgent));

// Theme values in one place
BrandPrimary = ColorValue("#9DFE0A");
SpacingM     = 16;

Why it’s better

  • No load-time cost — nothing runs until a screen needs it
  • Can’t go stale, unlike a variable set once in OnStart
  • Immutable — nothing else can overwrite it
  • Reads like a spreadsheet: define once, reference everywhere

Keep Set() for real state, e.g. the selected record — not for data you could derive.

Named formulas live in App.Formulas. They are lazily evaluated and recalculated automatically when their dependencies change, which is why they never go stale.

The classic anti-pattern is a 200-line OnStart that loads ten collections. Converting those to named formulas usually speeds up app start noticeably.

Module 2 · Power Fx

User-defined functions and With()

App.Formulas · user-defined functions
DaysOpen(created: DateTime): Number =
    DateDiff(created, Now(), TimeUnit.Days);

IsOverdue(created: DateTime, sla: Number): Boolean =
    DaysOpen(created) > sla;
Gallery item · Fill
If(IsOverdue(ThisItem.CreatedOn, 5),
   ColorFade(Color.Red, 85%), Color.Transparent)
btnClose · OnSelect
With(
    { r: LookUp(Referrals, Referral = varSelectedId) },
    Patch(Referrals, r, {
        Status:   'Status (Referrals)'.Closed,
        ClosedOn: Now()
    })
);
Notify("Referral closed", NotificationType.Success)

With() gives a formula local names — no global variable just to hold a lookup.

User-defined functions let you write business rules once and reuse them everywhere, with typed parameters. They live in App.Formulas next to named formulas.

With() scopes a value to one formula. Use it instead of Set() whenever the value is only needed inside that formula. If UDFs aren’t available in someone’s tenant yet, check the app’s Settings > Updates page.

Module 2 · Delegation

Delegation: let the server do the work

A delegable query runs at the data source. A non-delegable one pulls the first 500 rows (max 2,000) and filters locally.

No error, just missing data once the table grows. Treat the yellow triangle as a build failure.

Test with the row limit set to 1 in Settings to flush out delegation bugs early.

PatternDataverseSharePoint
Filter with = on textYesYes
StartsWithYesYes
Search / in substringYesNo
CountRows, SumYesNo
Sort on a columnYesSimple columns
Len, Lower inside a filterNoNo

Delegation is the number-one source of “the app worked in testing but not in production” bugs. The app silently works on a partial dataset.

Delegation support varies by connector and changes over time, so treat this table as a guide and always check the yellow warnings and the docs for the connector you use. This is also a big factor in choosing a data store, which W-T2 covers in depth.

Module 2 · Performance

Fast to open, fast to use

App.StartScreen and Screen.OnVisible
// App.StartScreen: deep links without OnStart navigation
If(!IsBlank(Param("id")), DetailScreen, HomeScreen)

// DetailScreen.OnVisible: load only what this screen needs,
// in parallel
Concurrent(
    Set(varReferral, LookUp(Referrals, Referral = GUID(Param("id")))),
    ClearCollect(colTeams, ShowColumns(Teams, Name, Region))
)
  • StartScreen instead of Navigate() in OnStart
  • Concurrent() for independent loads
  • ShowColumns — fetch only the columns you use
  • Fewer controls per screen; use galleries and components
  • Run App Checker and Monitor before every release

StartScreen is evaluated declaratively, so the app can render the first screen without waiting for OnStart. Concurrent runs independent calls in parallel.

Monitor (from Advanced tools) shows every network call with timings. It is the quickest way to find the one slow query that dominates load time.

Module 2 · Reuse

Components and accessibility

Components
  • Build headers, nav bars and status chips once
  • Custom input and output properties — no reaching into globals
  • Behaviour properties (e.g. OnBack) raise events to the host screen
  • Share through a component library in a solution; apps get update prompts
Accessibility
  • Set AccessibleLabel on every icon and image button
  • Check tab order and focus with the keyboard only
  • Contrast at least 4.5 : 1 for text
  • Don’t rely on colour alone for status — add text or an icon
  • Run the Accessibility checker in App Checker

Components are the canvas equivalent of reusable UI components in code. The key discipline: a component should only talk to the outside world through its properties.

Accessibility is a legal requirement for public-sector apps in the UK, not a nice-to-have. The built-in checker catches most of the basics.

Model-driven apps

Start with the data model; the UI follows. Business logic lives in Dataverse.

Module 3, about 20 minutes. Model-driven apps flip the approach: you design tables and relationships, and the platform generates a consistent, accessible UI.

Module 3 · Anatomy

Data first, then the app

TablesColumns, relationships, choices
Forms and viewsMain, quick create, quick view
Business process flowsGuided stages
App and sitemapNavigation and areas
Security rolesWho sees which rows

Design the data model on a whiteboard first: tables, relationships, ownership (user or team) and which columns are required.

Changing a table’s ownership type or a column’s data type after go-live is painful or impossible.

Walk left to right. Tables are where the real design work happens; forms, views and the app itself are mostly configuration.

Security roles are row-level: user-owned or team-owned tables plus business units decide who sees what. Get ownership right on day one.

Module 4 · Code Apps

Querying Dataverse from TypeScript

src/hooks/useAccounts.ts
import { useEffect, useState } from 'react';
import { AccountsService } from '../generated/services/AccountsService';
import type { Accounts } from '../generated/models/AccountsModel';

export function useAccounts(city: string) {
  const [rows, setRows] = useState<Accounts[]>([]);
  useEffect(() => {
    AccountsService.getAll({
      select: ['name', 'accountnumber', 'address1_city'],
      filter: `address1_city eq '${city.replace(/'/g, "''")}'`,
      orderBy: ['name asc'],
      top: 50,
    }).then((r) => setRows(r.data ?? []));
  }, [city]);
  return rows;
}

What to notice

  • select only the columns you need — always
  • filter, orderBy and top are delegated to Dataverse; page with skipToken
  • Escape quotes in OData strings
  • Also: get, create, update, delete — send only changed fields on update

This example uses the built-in Accounts table, as in Microsoft’s docs. The service returns a result object; the rows are on result.data.

Two Dataverse habits carry straight over from canvas: select only the columns you need, and on update send only the changed fields. Sending unchanged fields triggers business logic and pollutes the audit log.

Module 4 · Code Apps

Calling a flow from code

Terminal
pa app list-flows --search approval
pa app add flow --flow-id <flow-id>   # re-run after flow changes
src/actions/requestApproval.ts
import { ApprovalWorkflowService } from
  '../generated/services/ApprovalWorkflowService';

const result = await ApprovalWorkflowService.Run({
  requester: 'Alex',
  amount: 1500,
});
if (!result.success) console.error(result.error);

Rules

  • Only instant flows with the Power Apps trigger
  • The flow must be solution-aware
  • The developer adding it needs access to the flow and its connections
  • End users need Dataverse permissions to run it

Put server-side work — e-mails, approvals, integrations — in a flow, not the browser.

Calling flows directly from Code Apps arrived in 2026. The CLI downloads the flow’s OpenAPI definition and generates a typed Run method.

Scheduled and automated flows can’t be called this way. Check the generated file for the exact service name and result types.

Module 4 · Code Apps

ALM and current limitations

ALM
  • Source in your own Git repo — PRs, reviews, tests as normal
  • pa app push --solution-id places the app in a solution
  • Export and import that solution like any other
  • Same command interactively or in CI/CD (PA_CLI_SOLUTION_ID)
Limitations today
  • No Power Platform Git integration (use your repo)
  • Assets served from a public endpoint — restrict with Conditional Access, not IP binding
  • No SharePoint forms integration or Power Apps for Windows
  • No Secure Implicit Connections yet

Check the Microsoft Learn limitations page before each project — this list is shrinking fast.

The good news for developers: Code Apps fit a normal Git workflow, with unit tests and Playwright end-to-end tests like any React app.

The limitations listed are from Microsoft’s documentation at the time of writing. Confirm them before committing a design, especially the security ones.

05

Power Automate that doesn’t fail silently

Error handling, reuse and throughput for flows you can run in production.

Module 5, about 20 minutes. Most production incidents in Power Platform are flows that failed and nobody noticed.

Module 5 · Error handling

Try / catch / finally with scopes

Scope: Try
Get row
Call API
Update row

Runs normally

Scope: Catch
Filter failed actions
Alert the team
Terminate: Failed

Run after Try: has failed, has timed out

Scope: Finally
Log the run
Release lock

Run after Catch: all four outcomes

Without Terminate: Failed, a handled error shows as Succeeded in run history — and your monitoring misses it.

Scopes plus “Configure run after” give you structured error handling. Catch only runs when Try fails or times out; Finally runs whatever happens.

Note that Finally is set to run after Catch with all outcomes ticked, including skipped, otherwise it won’t run on the happy path.

Module 5 · Expressions

Expressions for the Catch scope

Expressions
// Filter array · From: every action result inside Try
result('Try')
// Filter array · condition: keep only the failures
@equals(item()?['status'], 'Failed')

// A link to this run, for the alert
concat('https://make.powerautomate.com/environments/',
  workflow()?['tags']?['environmentName'], '/flows/',
  workflow()?['name'], '/runs/', workflow()?['run']?['name'])

// Safe defaults and null-safe access
coalesce(triggerBody()?['priority'], 'Normal')

// Due date from an environment variable
addDays(utcNow(), int(parameters('SLA days (kna_SlaDays)')))
  • result('Scope') returns the outcome of every action inside a scope
  • The run link lets whoever gets the alert jump straight to the failure
  • Use ?[ ] everywhere: missing properties return null instead of failing
  • Environment variables appear as parameters in solution flows

These are the expressions we use in almost every production flow. The run URL is the single most useful thing in an alert e-mail.

Environment variables show up in the dynamic content pane under their display name; the exact parameter name in the expression comes from that display name and schema name.

Module 5 · Reuse and throughput

Child flows, concurrency and retries

TechniqueWhat it doesWatch out for
Child flowsReusable logic called with Run a Child Flow; returns data with Respond to a Power App or flowBoth flows must be in a solution; set the child’s run-only connections
Trigger concurrencyLimits how many runs execute at onceSet to 1 when order matters; it can’t be switched off again once set
Apply to each concurrencyProcesses items in parallel (up to 50)Don’t set variables inside a parallel loop — use Compose
Retry policyDefault: exponential, 4 retries; or fixed / noneUse none for non-idempotent calls, e.g. payments
PaginationList rows returns 5,000 rows by defaultTurn on pagination or use $filter; avoid loops over big tables

Child flows are the flow equivalent of functions. They are the main way to stop copy-pasting the same 20 actions across ten flows.

The concurrency and retry settings are on each action’s Settings tab. Most performance problems in flows are loops that should have been a single filtered query.

06

Connectors, solutions and ALM

Making apps and flows portable, governable and safe to deploy.

Module 6, about 20 minutes. Everything we built today is only valuable if we can move it safely from dev to test to production.

Module 6 · Governance

Connectors and data loss prevention

Businesse.g. Dataverse, SharePoint, Outlook, Teams
Non-businesse.g. social media, personal storage
BlockedCan’t be used at all

An app or flow can’t mix business and non-business connectors.

  • Standard vs premium connectors drive licensing
  • Custom connectors wrap your own APIs (OpenAPI), with OAuth or API key
  • Classify custom connectors in DLP too — they default to non-business
  • A tenant-wide policy plus stricter ones per environment
  • Lock down the default environment hardest
  • Endpoint filtering limits HTTP and SQL to approved hosts

DLP policies group connectors so business data can’t flow into non-business services in the same app or flow. Blocked connectors can’t be used at all.

The default environment is where every licensed user can create things, so it needs the strictest policy. Real work belongs in dedicated environments.

Module 6 · Solutions

Solutions: the unit of deployment

UnmanagedManaged
WhereDevelopment onlyTest and production
EditableYesNo — locked components
Delete solutionRemoves the container, leaves the componentsRemoves the components cleanly
UpgradesOverwriteVersioned layers, clean upgrades

Create your own publisher with a short prefix (e.g. kna_) before the first table. It’s baked into every schema name.

Never use the Default Solution or cr123_ prefix, and never edit in test or prod — it creates an unmanaged layer.

Rule one: unmanaged in dev, managed everywhere else. Managed solutions are the only way to get clean upgrades and clean removal.

The publisher prefix appears in every table and column name forever, so agree it as a team on day one.

Module 6 · Configuration

No hard-coding: variables and references

Environment variables

Text, number, yes/no, JSON, data source (e.g. a SharePoint site) and secret (from Azure Key Vault). One value per environment.

Connection references

A named pointer to a connection. Flows and apps use the reference; each environment binds it to its own connection, ideally a service account.

deploy/test.settings.json
{
  "EnvironmentVariables": [
    { "SchemaName": "kna_SlaDays", "Value": "3" },
    { "SchemaName": "kna_ApiBaseUrl",
      "Value": "https://api-test.contoso.com" }
  ],
  "ConnectionReferences": [
    { "LogicalName": "kna_sharedoffice365_ref",
      "ConnectionId": "<test-connection-id>",
      "ConnectorId":
        "/providers/Microsoft.PowerApps/apis/shared_office365" }
  ]
}

Environment variables replace every hard-coded URL, site ID, e-mail address and threshold. Secret variables read from Key Vault, so no secrets in solutions.

The settings file supplies values at import time, so a pipeline can deploy unattended. pac solution create-settings generates a blank one from a solution zip.

Flight rules

Rules that speed you up

  • Never build in the default environment
  • Everything in a solution, with your own publisher prefix
  • No hard-coded values — environment variables
  • Connection references, owned by a service account
  • Managed only outside dev; never edit in test or prod
  • Delegation warnings are build failures
  • Every flow has try / catch / finally and alerts
  • Named formulas over OnStart collections
  • DLP policy on every environment
  • Code Apps: never hand-edit generated/
