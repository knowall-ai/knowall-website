What good looks like

From commit to production

Pull requestBuild validation, review, policies
Build onceTest, scan, version, publish artifact
TestBicep + app, deployed automatically
ChecksApproval, branch control, alerts
ProductionSame artifact, slot swap

Build once: the artifact you tested is the one you ship.

No stored secrets: federated identity and Key Vault.

People decide: humans approve production; machines do the rest.

This is the pipeline the demos build by the end of the morning. Every box maps to a module.

Why bother: the DORA research measures delivery with deployment frequency, lead time for changes, change failure rate and time to restore. Good CI/CD improves all four at once, because each change is small and goes through the same checks every time.

Note the artifact is built once and promoted. Environment differences live in configuration, never in a rebuild. Ask the room: how long does a one-line fix take to reach production today?

Live demo

A pull request that proves itself

  1. Add a build validation policy to mainDirect pushes to main are now blocked
  2. Open a PR with a failing unit testValidation fails; the test shows on the PR’s Tests tab
  3. Fix the test and push againValidation re-runs and passes; the cache restore is quick
  4. Complete the PR with squash mergeCI on main publishes artifact web with a new version

Module 1, continuous integration: merge small changes to main often, with an automated build proving each one works. If a build is red, fixing it is the team's top priority.

Demo in the sample project. Show the branch policy screen: build validation, at least one reviewer who isn't the author, a linked work item and resolved comments. For Azure Repos Git this policy is how PR validation works; the YAML pr keyword only applies to GitHub and Bitbucket repos. Then show the failed PR run and its Tests tab.

Point out the second run is faster because of the cache hit: a slow pipeline is a pipeline people work around, so aim for feedback in under ten minutes. Finish on the artifact and run number on main; that one artifact is what every later demo promotes.

Prep: have the sample repo and a pipeline that already builds green, plus a branch with a deliberately failing test ready to push. Keep a screenshot of each step in case the hosted agents queue slowly.

Module 2 · YAML pipelines

Stages, jobs, steps — and templates

  • Pipelineone YAML file in the repo
  • StageBuild, DeployTest, DeployProd
  • Jobruns on one agent
  • Stepscript or task
  • Stages run in sequence; jobs in a stage run in parallel
  • Templates with typed parameters stop copy-paste
  • extends + a Required template check: only the approved path reaches production
azure-pipelines.yml
stages:
  - stage: Build
    jobs:
      - job: build
        steps:
          - template: templates/node-build.yml
            parameters: { runTests: true }

  - stage: DeployTest
    dependsOn: Build

  - stage: DeployProd
    dependsOn: DeployTest

A pipeline is a tree. Stages group jobs, jobs get an agent, steps run on that agent.

Templates take typed parameters and expand into steps, jobs or stages. Keep shared templates in their own repo and pin consumers to a tag. With extends, a platform team's template wraps the whole pipeline and adds scanning and approved agents; the Required template check on production means nothing else can deploy.

Demo it live: open the pipeline editor, move the build steps into a template, run it, and show the expanded YAML in the run log. Mention the three variable syntaxes only if asked: parameters shape the pipeline at compile time, macros feed tasks, runtime expressions read values from earlier jobs.

Module 3 · Release

Environments, approvals and checks

People
  • Approvals by a person or group
  • Block self-approval by the person who queued the run
  • Set a timeout
Policy
  • Branch control: only main or release/*
  • Required template
  • Business hours
  • Exclusive lock: one deployment at a time
Signals
  • Query Azure Monitor alerts
  • Invoke REST API or Azure Function, e.g. change ticket status
  • Evaluate artifact policies

Checks belong to the environment, not the YAML — so nobody can remove them in a pull request.

A deployment job targets an environment. That one line connects the YAML to approvals, checks and deployment history: which run, commit and work items went where.

Checks are configured on the protected resource: the environment, service connection, agent pool or variable group.

Because they are not in the YAML, a developer can't bypass them by editing the pipeline. That's why production approvals should always live here.

Automated checks such as alerts and change tickets let you remove manual steps over time.

For App Service, zero downtime comes from deployment slots: deploy to staging, smoke test, swap. Rollback is another swap. Mark environment-specific settings as slot settings, and keep database changes backwards compatible. Branching: Release Flow keeps main always releasable, with short-lived topic branches and release branches cut per sprint.

Module 4 · Identity

Service connections without secrets

Pipeline jobUses service connection sc-app-test
Short-lived tokenIssued by Azure DevOps for this job (OIDC)
Microsoft Entra IDFederated credential trusts that issuer and subject
AzureAccess token, scoped by RBAC
  • Workload identity federation: no client secret to store, leak or rotate
  • Backed by an app registration or a user-assigned managed identity
  • Any secret you still need comes from Key Vault, masked in logs

Least privilege: one connection per environment, scoped to its resource group, with a role such as Contributor — not Owner on the subscription.

Workload identity federation replaces stored client secrets. The job gets a short-lived token from Azure DevOps, and Entra ID exchanges it for an Azure access token because a federated credential trusts that exact connection.

Existing secret-based connections can be converted in place. Separate connections per environment mean a test pipeline can never touch production.

When a secret is unavoidable, pull it with the Key Vault task or a variable group linked to a vault. Better still, the app reads Key Vault with its own managed identity so the secret never passes through the pipeline. Never echo secrets: masking can't catch transformed values.

Live demo

Create a federated service connection

  1. Project settings → Service connections → Azure Resource ManagerWorkload identity federation is the recommended option
  2. Scope it to rg-app-test and name it sc-app-testAn identity is created with a federated credential

Module 5 · Infrastructure-as-code

Environments you can rebuild from Git

Bicep: one template, every environment

  • Modules for reuse; one parameter file per environment
  • What-if shows what will change before anything happens
  • Infrastructure deploys before the app in each stage
  • Stop drift: read-only portal access, deployment stacks, Azure Policy
BicepTerraform
CloudsAzure onlyMulti-cloud and SaaS providers
State fileNone — Azure is the stateMust store and lock it
Preview changeswhat-ifplan
Best forAzure-centric teamsMixed estates

If an environment can only be rebuilt from memory and portal clicks, it isn't really under control. We use Bicep for Azure: it compiles to ARM, so anything Azure supports, Bicep supports on day one.

Drift happens when someone fixes production in the portal; the next deployment either undoes the fix or fails. Both Bicep and Terraform are good choices; for an Azure-only estate Bicep has less to manage because there's no state file.

Live demo

Preview, then deploy, from the pipeline

  1. Walk through infra/main.bicep and infra/test.bicepparamOne template; the parameter file holds the test values
  2. Add an AzureCLI@2 step running az deployment group what-if with sc-app-testThe run log lists resources to create, change or delete
  3. Add az deployment group create after it, then run the pipelinerg-app-test fills up; the deployment is named after the build
  4. Change a setting in the portal, then run what-if againWhat-if shows the drift it would undo

Both commands run as the federated connection from the last demo. Naming the deployment after the build ID gives a deployment history in the resource group that maps back to the pipeline run.

The portal change is the drift moment: show that the next deployment would quietly put it back. For production, put an approval between what-if and deploy.

Prep: keep the Bicep files small (an App Service plan and web app is enough) so the deployment finishes in a minute or two.

Module 6 · Power Platform

Solutions through source control

Dev environmentMakers build in an unmanaged solution
ExportUnmanaged .zip
UnpackReadable XML and files
Commit + PRReviewed diff
Pack managedBuilt from Git
ImportTest, then prod, with settings
  • Git is the source of truth, not the dev environment
  • Managed solutions only beyond dev
  • Bump the solution version on every build

Pitfall: importing unmanaged solutions into test or production. You can’t cleanly remove or upgrade them later.

Export from dev, unpack into source files, review them in a pull request, then build a managed solution from Git and import it downstream.

Use the Power Platform Build Tools tasks in YAML, or the pac CLI (export, unpack, pack, import) locally and in GitHub Actions. A deployment settings file sets environment variables and connection references per environment, so there are no manual fix-ups after import.

Pipelines in Power Platform is the in-product option for makers: quick to adopt, but no pull request review. Use Azure DevOps with Build Tools for solutions that matter or ship alongside Azure resources and code. Run the solution checker in the build. W-T3 covers solutions and environments in more depth.

Live demo

A Power Platform solution through Git

  1. Run the export pipeline against the dev environmentA PR with the unpacked solution as readable files
  2. Review the diff and complete the PRThe change to the app or flow is visible line by line
  3. Run the release pipeline: pack as managed, run the solution checkerA managed solution artifact and a checker report
  4. Import to test with config/test.settings.jsonEnvironment variables and connection references set; no manual fix-ups

This is the same pattern as the app pipeline: source in Git, review in a PR, build once, promote with per-environment settings.

Prep: dev and test environments, service connections that authenticate as an application user in each, and the connections in test created up front by a service account. Check the current Build Tools task versions in the Marketplace beforehand.
