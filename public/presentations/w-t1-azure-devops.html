the delivery flight deck

Backlogs, boards, queries, test plans, repos and automation — a demo-led half day for engineers, tech leads, product owners and testers.

Welcome everyone, introduce yourself and the format: six short modules, each a few minutes of slides and then a live demo in a real Azure DevOps project. Slides stay light on purpose; the demos carry the detail.

Set expectations: this is about running delivery day to day in Azure DevOps, the way the T-Minus-15 process uses it. Azure DevOps only helps if it is the single source of truth, with traceability from epic to story to commit to test.

Ask the room: who already uses Boards, Repos, Test Plans? Which pain points do they have: work tracked in spreadsheets and chat, stories with no acceptance criteria, direct pushes to main, weekly status reports? Adjust the depth of each demo accordingly.

Module 1 · Organisation and process

Structure, process and work items

  • Orgdev.azure.com/contoso
  • ProjectDelivery
  • TeamApps squad
  • AreaDelivery\Apps
  • IterationDelivery\2026\Sprint 21
  • Project — a security and process boundary; teams see work through area paths, sprints through iteration paths
  • Process — the system processes are locked; customise an inherited one (T-Minus-15 inherits from Agile)
  • Backlog — Epic → Feature → Story → Task, plus Bug, Enhancement, Issue, Risk and Question
  • AMP criteria on every story — Acceptance (Gherkin), Measure, Proof

Tip: prefer fewer, larger projects with many teams. Cross-project queries and reporting are harder.

One slide for the whole structure. Organisation at the top, connected to Entra ID. A project is the boundary for process and permissions; teams live inside it and see work through area paths. Areas answer "what", iterations answer "when".

Process: the four system processes (Basic, Agile, Scrum, CMMI) can't be edited, so customise an inherited process. Recommend inheriting from Agile; the T-Minus-15 template is exactly that, with extra work item types.

Bug versus enhancement: a bug means the story did not meet its acceptance criteria; an enhancement is an improvement that does not block acceptance. AMP puts testable Gherkin, numbers and proof in the Acceptance Criteria field, precise enough for a tester, a developer or an AI agent. Then go straight to the demo.

Module 2 · Backlogs and boards

A board that shows where work is stuck

NewCaptured, not ready
ReadyAMP criteria agreed
In progressWIP 4
Review / testWIP 3
DoneMeets the DoD
  • Columns map to states; split columns show work waiting to be pulled
  • WIP limits turn red when exceeded — stop starting, start finishing
  • Definition of Done per column, shown on the board
  • Swimlanes for an Expedite lane; card styles to flag blocked work
  • Sprints: capacity per person, tasks with Remaining Work
  • Track with the taskboard, burndown, velocity and cumulative flow

Board columns are configured per team and per backlog level and map onto the process states. WIP limits are advisory: the count turns red but nothing is blocked. The point is to make the bottleneck visible and talk about it at stand-up.

Sprints: set capacity per person and days off, break stories into tasks with Remaining Work. A flat burndown usually means Remaining Work isn't being updated, not that nobody is working.

Module 3 · Queries and dashboards

Ask the data, don’t ask the team

Query typeUse it for
Flat listLists, charts, bulk edits
Direct linksStories with no test cases; bugs linked to a story
Tree of work itemsEpic → Feature → Story roll-ups
  • Every query is WIQL underneath; macros like @Me and @CurrentIteration
  • Save to Shared Queries so dashboards and alerts can use them
  • Team dashboards: sprint goal, burndown, query tiles and charts, build status
  • Analytics views or OData with Power BI for portfolio and trend reporting

Quality check query: User Stories that do not have a Tested By link find stories nobody has written tests for.

Three query types. Flat lists are the default and the only type that supports charts. Direct links find items with or without a particular link, which is great for quality checks. Tree queries show the hierarchy.

The editor doesn't show WIQL text; the WIQL Editor extension or the REST API does. Personal queries can't be used on dashboards, so save team queries under Shared Queries.

For anything across projects or over long periods, use Analytics: Analytics views in Power BI, or OData with $select and $filter.

Module 4 · Test Plans

From story to test run to bug

User StoryAMP criteria
Test caseTested By link
Test runManual or automated
BugCreated from the failed step
RetestStory accepted
  • Plan → suite → case; one requirement-based suite per story
  • Query-based suites for regression packs; shared steps for sign-in
  • The Test Runner records pass or fail per step, with screenshots
  • Automated test results from a pipeline can be associated with test cases

Creating and managing test plans needs the Basic + Test Plans access level. Check licences before the team relies on it.

This is the traceability chain auditors and product owners care about. Each AMP scenario becomes a test case and each Proof line a test case ID. The story links to its test cases via Tested By; runs record results; a bug created from a failed step carries the repro steps automatically.

One test plan per sprint or release. Requirement-based suites roll results up to the story. Licensing: check the current licensing page before promising anything.

Module 5 · Repos and pull requests

Short branches, protected main

Topic branchDays, not weeks
Pull requestPolicies, review, build
mainAlways releasable
releases/2026.11Cut per release
  • Release Flow: all PRs target main; no long-lived develop branch
  • Hotfix in main first, then cherry-pick to the release branch
  • A PR template pre-fills what, why, how to test and a checklist
  • Policies on main: reviewers, linked work items, comment resolution, build validation
  • Squash merge for a readable history
  • Link work with #1042, or AB#1042 from GitHub

Release Flow is trunk-based development with short topic branches and release branches cut when you ship. The hotfix rule is "main first, then cherry-pick", so a fix is never lost in the next release.

Once any policy is on, direct pushes to main are blocked. Reset votes on new pushes, and use path-based required reviewers like a CODEOWNERS file. Policies can be set per repo, at project level, or scripted with az repos policy.

A PR template lives in the .azuredevops folder. Creating the branch from the story's Development section links everything automatically.

Module 6 · Automation

CLI, REST and service hooks

Script it
  • az devops, az boards, az repos, az pipelines for setup and bulk changes
  • The REST API for everything else; pin the api-version
  • Authenticate with Entra ID tokens or managed identities; a PAT is a last resort
React to events
  • Service hooks fire when work items, PRs or builds change
  • Call a Logic App or Function with a managed identity: no secrets
  • Example: T-Minus-15’s effort-rollup recalculates an Epic from its Features

Pipelines: a YAML PR build wired in through the build validation policy is enough here. Multi-stage pipelines, approvals and Bicep are in W-T4 CI/CD.

Keep this short and show it live in a terminal: run az boards query with a small WIQL query against the demo project, and create one work item with az boards work-item create. Then open Project settings, Service hooks to show the subscription options.

Microsoft is steering everyone towards Entra ID tokens and away from PATs. Services should use a managed identity or service principal added to the organisation, so there is no secret to leak or rotate.

Watch for loops: an automation that updates a work item can trigger itself, so filter the subscription on the fields you care about. Don't get pulled into pipelines; point to W-T4.

Recap

Flight rules, and where to go next

Flight rules
  • One project, many teams: areas for what, iterations for when
  • Inherit, don’t fork, the process
  • No story enters a sprint without AMP criteria
  • WIP limits on every board; talk about red columns
  • Protect main; link every PR to a work item
  • Shared queries and dashboards, not status reports
  • No PATs in code: Entra tokens and managed identities
Optional deep dives
  • W-T4 CI/CD — multi-stage YAML, environments, approvals, Bicep
  • W-T5 Agentic coding — agents that work from your backlog
  • Process customisation: fields, rules, states
  • Analytics and Power BI portfolio reporting
  • Migrating from Jira or spreadsheets

Recap by flicking back through the demo project: the backlog, the board, the dashboard, the tested story and the merged PR, all linked together. That traceability is the takeaway.

The flight rules are the short list to adopt; suggest they pin this slide to the team wiki. Then point to the follow-ups: W-T4 for pipelines, W-T5 for agentic coding, and deep dives on process customisation, reporting or migration if the team needs them.
