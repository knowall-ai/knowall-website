Why it matters

Three stores, one hard-to-undo decision

Dataverse

Business data platform
  • Relational tables with rich types
  • Role-based security built in
  • Native to model-driven apps and solutions

SharePoint

Documents and simple lists
  • Already licensed with Microsoft 365
  • Great for documents and metadata
  • Flat lists, limited relationships

Azure SQL

Full relational engine
  • T-SQL, views, stored procedures
  • Scales to very large volumes
  • Shared by apps, APIs and reporting

Data outlives every app built on it. The store fixes your security model, scale ceiling and licence bill — and “we’ll move it later” rarely happens.

Set the scene: screens can be rebuilt in a sprint, but once records, relationships and permissions exist, moving them is a project in its own right. Most “Power Apps is slow” complaints are really data and delegation problems.

One-line positioning for each: Dataverse is a managed business data platform, SharePoint is a collaboration platform that happens to store lists, and Azure SQL is a general-purpose relational database. There is no single right answer, only the right store for each kind of data.

Modules 1 and 2 · Dataverse

Model it once, secure it properly

Modelling
  • Table types: standard, activity, elastic (high volume) and virtual (data stays outside)
  • Relationships: 1:N lookups and N:N, with cascade rules on delete and assign
  • Logic in columns: choices, formula and rollup columns, business rules
  • Build inside a solution with your own publisher prefix
Security
  • Security roles grant privileges per table, to a depth: user, business unit or organisation
  • Roles are additive; assign them through Entra group teams
  • Column security masks sensitive fields
  • Auditing records who changed what, and when

Some choices are permanent: table ownership and logical names can’t be changed later. Choose user/team ownership if you will ever need row-level security.

This one slide covers the first two modules; the detail comes in the two demos that follow. Standard tables cover most needs. Elastic tables trade relational features for scale; virtual tables show external data in place.

On security, read it as: people belong to teams, teams and people hold roles, roles grant privileges to a depth, and depth is measured against business units. Start from a minimal role and add to it, never from System Administrator.

Record sharing is for exceptions only. If you find yourself sharing thousands of rows, redesign with business units or owner teams.

Module 3 · SharePoint

Brilliant for documents, with clear edges

Good fit

  • Documents with metadata, versioning and co-authoring
  • Simple lists: a few thousand rows, few relationships
  • Team-level data where site permissions are enough

Know the edges

  • A query that scans more than 5,000 items is blocked — index filter columns early
  • Item-level permissions don’t scale; there is no real row-level security
  • Many related lists and complex lookups get slow

A common hybrid: structured records in Dataverse or SQL, with their documents in a SharePoint library.

SharePoint is not the enemy; it is the best place for documents. Problems start when lists are used as a relational database.

The 5,000 list view threshold limits how many items one query can scan, not how many the list can store, and it can’t be raised in SharePoint Online. Make the security point firmly: filtering a gallery in Power Apps is not security.

Module 4 · Azure SQL

A full relational engine, locked down

App or FunctionManaged identity
Entra IDIssues the token
Private endpointNo public access
Azure SQLRow-level security
  • vCore tiers for most new work; serverless for dev and quiet apps
  • Entra-only authentication: no passwords in connection strings
  • Row-level security in the engine applies to every client
  • Automatic backups with point-in-time restore; the connector is premium

The target pattern: no SQL logins, and the database reachable only through a private endpoint. Power Platform reaches a private database through a data gateway or virtual network support, so plan that early.

Row-level security has one catch: if every request arrives as one service identity, SQL can’t tell users apart. Connect as the signed-in user, or set SESSION_CONTEXT from a trusted API.

Module 5 · Delegation and scale

Who does the filtering?

Delegable

AppSends the query
Data sourceFilters all rows

Not delegable

Data sourceReturns first 500
Silently wrongRows 501+ ignored
  • Treat the delegation warning in Studio as a bug; keep the column bare on the left of a comparison
  • Dataverse and SQL delegate far more than SharePoint (for example Search and in)
  • Every store throttles: batch, page and honour 429 and Retry-After

Delegation means pushing the work to the data source. When a formula can’t be delegated, Power Apps fetches only the first 500 rows (up to 2,000 if raised) and works on those, so results are silently incomplete once the data grows.

The commonest cause is wrapping the column in a function such as Year or Lower. Delegation support changes between releases, so trust the warning and check the connector documentation.

Price the whole solution, not the store: once one premium connector is in the app, every user needs a premium licence anyway.

Fill this in live for the asset tracker, with the room. The colours are a starting point, not a verdict: weight each row by what matters for the solution in front of you.

A quick decision flow for first conversations: mostly documents, SharePoint library; very large, shared or needs T-SQL, Azure SQL; row-level security, relationships or growth, Dataverse; small, simple and team-only, SharePoint list. Don’t quote prices: check current Microsoft pricing, as entitlements change.

Recap

Rules that save you a migration

  • Choose per kind of data — hybrids are normal
  • Decide security first — row-level access rules SharePoint lists out
  • Treat delegation warnings as bugs
  • No passwords — Entra ID and managed identities
  • Record the decision and what would make you revisit it
