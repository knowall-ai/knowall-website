Why it matters

From autocomplete to agents

AutocompleteSuggests the next line. You drive every keystroke.
ChatAnswers questions and drafts snippets. You copy, paste and run.
AgentsRead the repo, edit files, run tests and iterate until the goal is met.

The shift: the unit of work moves from a line of code to a task. Your job moves from typing to specifying, reviewing and deciding.

The catch: an agent can be confidently wrong, fast. Without clear specs and reviews, speed just produces more rework.

Most teams have used autocomplete and chat. Agents are different because they act: they read files, run commands and check their own work in a loop.

That changes what engineers spend their time on. Writing good specs and reviewing changes become the core skills, which is why the T-Minus-15 Prep and Test stages matter even more with agents.

01

What agentic coding is

The agent loop, and an honest view of where agents help and where they don’t.

Module 1 is the mental model. Fifteen minutes, mostly discussion. Ask the room who has already used an agent on a real codebase, and what surprised them.

Module 1 · What agentic coding is

The agent loop

GoalA task with clear acceptance criteria
PlanRead the code, propose an approach
ActUse tools: edit files, run commands
ObserveRead test output, errors, diffs
Human reviewApprove, redirect or reject

Plan → act → observe repeats until the goal is met, or the agent stops and asks.

What makes it work
  • A verifiable goal: tests, a build, a checklist
  • Tools the agent can actually run
  • Context: conventions, architecture, commands
What breaks it
  • Vague goals with no way to check “done”
  • No tests, so the agent can’t observe failure
  • Huge tasks that overflow the context window

The key idea is the feedback loop. An agent is only as good as its ability to observe whether it succeeded, so tests and builds are its eyes.

Point out the human review step: it is not optional. The agent proposes, people decide what ships.

Module 1 · Decision

Where agents help, and where they don’t

TaskFitWhy
Well-specified feature with testsStrongClear goal, fast feedback loop
Writing tests from acceptance criteriaStrongCriteria map directly to test cases
Refactoring, upgrades, migrationsStrongRepetitive, mechanical, verifiable by the build
Explaining unfamiliar codeStrongReads faster than people; no changes made
Debugging with a reproducible failureGoodWorks well once the bug can be reproduced
Architecture and trade-off decisionsAssistGood at options; people own the decision
Vague requirements, no testsWeakNothing to verify against — fix the spec first
Security-critical or regulated logicHuman-ledAgents can help, but sign-off stays with people

Use this table to set expectations. The pattern: agents shine where the goal is clear and the result can be checked automatically.

Where requirements are vague, the right move is not a better prompt but a better story. That is Module 4.

Worktrees let you run two agents on two tasks without them treading on each other’s files.

Module 2 · Project memory

CLAUDE.md: the onboarding doc for agents

CLAUDE.md
# Orders service

## Commands
- Install: `npm ci`
- Test: `npm test` (Vitest) · E2E: `npm run e2e` (Playwright)
- Lint and types: `npm run lint && npm run typecheck`

## Architecture
- Next.js App Router in `app/`, data access only in `lib/db/`
- API routes validate input with Zod schemas in `lib/schemas/`

## Rules
- Work on a branch; never commit to `main`
- Every change needs a test that fails without it
- Never read or write `.env*` files
- Sample data only — no real customer records

See @docs/architecture.md for the data model.

Where it lives

  • Project: ./CLAUDE.md, committed and reviewed
  • Personal: ~/.claude/CLAUDE.md
  • Imports: @path pulls in other docs

Keep it short and specific. Commands and rules beat essays.

CLAUDE.md is loaded into every session, so it is the cheapest way to stop the agent repeating mistakes. Treat it like code: commit it and review changes to it in pull requests.

A good test: would a new human developer find this useful on day one? If yes, it belongs here.

Module 2 · Control

Plan mode and permission modes

ModeWhat the agent can doUse it for
planRead and research only; proposes a plan, makes no changesAnything non-trivial: agree the approach first
manualAsks before each edit or commandUnfamiliar repos, learning the tool
acceptEditsEdits files freely; still asks for other commandsDay-to-day work on a branch
autoA safety check reviews each action instead of a promptLonger tasks with trusted rules in place
dontAskAnything not pre-allowed is denied, not askedHeadless runs with a strict allow list
bypassPermissionsNo checks at allOnly in an isolated sandbox

Habit: start in plan mode, read the plan, then switch to acceptEdits to execute. Shift+Tab cycles modes; --permission-mode sets one at launch.

These are the modes accepted by --permission-mode in current Claude Code; names change between versions, so check claude --help on your install.

Plan mode is the single biggest quality lever. Reviewing a plan takes a minute; reviewing a wrong implementation takes an hour.

Module 2 · Control

Permission rules as code

.claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(npm run test *)",
      "Bash(npm run lint)",
      "Bash(git status)", "Bash(git diff *)"
    ],
    "ask": [ "Bash(git push *)" ],
    "deny": [
      "Read(./.env*)",
      "Bash(rm -rf *)",
      "WebFetch"
    ]
  }
}

How rules apply

  • deny wins over ask, ask over allow
  • Project settings are committed; settings.local.json stays personal
  • Organisations can enforce managed settings that users can’t override

Command patterns are a convenience, not a sandbox. Isolate risky work in a container or VM.

Pre-approving safe, frequent commands removes most of the prompt fatigue, which is what tempts people into bypassing permissions altogether.

Be honest about limits: a pattern like rm -rf can be worked around by a determined or confused agent, so real isolation comes from the environment, not the rule list.

03

Skills and specialist agents

Package your team’s know-how so every agent follows it.

Module 3 is where agentic coding starts to scale. Instead of repeating instructions in every prompt, you capture them once as skills and specialist agents and share them across the team.

Module 3 · Building blocks

Skills, subagents and plugins

SkillSubagentPlugin
What it isInstructions and files for one kind of taskA specialist with its own prompt, tools and contextA bundle of skills, agents, hooks and MCP servers
Where it lives.claude/skills/<name>/SKILL.md.claude/agents/<name>.mdA marketplace or Git repo
How it runsLoaded when relevant, or /nameDelegated to; works in a separate contextInstalled with /plugin
Use it for“How we create a PR”“A tester who reviews coverage”Sharing the lot across teams

A simple way to remember it: a skill is a recipe, a subagent is a colleague, and a plugin is how you share both.

Subagents are also a context-management tool: a big search runs in the subagent’s context and only the summary comes back.

Module 3 · Skills

Anatomy of a skill

.claude/skills/create-pr/SKILL.md
---
name: create-pr
description: Our Definition of Done for a pull request.
  Use whenever asked to open or create a PR.
---

# Create a pull request

1. Branch from `main`: `feature/<story-id>-<slug>`
2. Run `npm run lint`, `npm test`, `npm run e2e`
3. PR title: `AB#<story-id> <summary>`
4. Body: what changed, why, how it was tested,
   screenshots for UI changes
5. Link the work item; request a human reviewer
6. Never merge your own PR

Template: see ./pr-template.md

What matters

  • The description decides when the skill is used — say when, not just what
  • Steps are checkable, not aspirational
  • Supporting files sit beside SKILL.md and load only when needed

The T-Minus-15 plugin ships skills like user-story, create-pr and e2e-tests.

A skill is plain Markdown with a short YAML header. Only the name and description are loaded up front; the body loads when the skill is relevant, so you can have many skills without filling the context.

Write the description like a trigger: when should the agent reach for this?

Module 3 · Subagents

A specialist reviewer

.claude/agents/reviewer.md
---
name: reviewer
description: Reviews a branch for correctness, tests and
  security before a PR. Use proactively after changes.
tools: Read, Grep, Glob, Bash
---

You are a senior reviewer. You never edit files.

For the current branch versus `main`:
1. Check every acceptance criterion has a test
2. Look for unvalidated input, secrets, injection
3. Run `npm test` and report failures
4. Return findings ranked by severity, each with
   file:line and a suggested fix

Design choices

  • Read-only tools: a reviewer that can’t edit can’t “fix” quietly
  • Own context: reads the whole diff without cluttering yours
  • Manage with /agents; run one for a session with --agent

Restricting tools is the key design decision. A reviewer agent should report, not change code, so the human sees every finding.

The T-Minus-15 agents follow the same format: Markdown, a YAML header with name, description and tools, then the persona and process.

04

Specs and prompts

Agents build exactly what you ask for. Ask for the right thing.

Welcome back from the break. Module 4 is the highest-value skill in the whole workshop: writing specifications an agent can execute and verify.

Module 4 · From story to spec

AMP acceptance criteria

User story 1234 · Filter orders by status
Acceptance (A)
SCENARIO: Filter the order list by status
GIVEN 20 sample orders, 5 with status "Shipped"
WHEN  the user selects "Shipped" in the status filter
THEN  exactly 5 orders are listed
AND   the URL contains ?status=shipped

Measure (M)
- List updates within 500 ms for 1,000 orders
- Zero accessibility violations (axe)

Proof (P)
- TC1: Playwright test orders-filter.spec.ts
- Unit test: filterOrders() covers every status

Why AMP suits agents

  • Acceptance: Gherkin the agent can turn into tests
  • Measure: numbers, so “fast” isn’t a matter of opinion
  • Proof: names the tests that show it’s done

Specific, measurable, observable, binary: each line passes or fails.

AMP is the T-Minus-15 format for acceptance criteria. It was designed so that a developer, human or agent, can build the feature, verify it and prove it.

Notice the sample data in the GIVEN line: the agent can create exactly that fixture and test against it.

Module 4 · Prompts

The same task, two prompts

Vague
prompt
Add filtering to the orders page
and make it fast.
  • Filter by what? Where in the UI?
  • “Fast” can’t be checked
  • No idea when to stop
Executable
prompt
Implement story 1234 (criteria below) on a new branch.

Context: list page is app/orders/page.tsx; queries live
in lib/db/orders.ts. Follow the existing Zod pattern.

Constraints: no new dependencies; don't change the API
response shape.

Done when: TC1 and the unit test pass, lint and
typecheck are clean. Plan first and wait for my OK.

[AMP criteria pasted here]

The good prompt has four parts: the goal with criteria, context on where to look, constraints on what not to do, and a definition of done the agent can check.

Asking for a plan first turns a one-shot gamble into a conversation.

Module 4 · Patterns

Habits that pay off

Size it

One story per session. If the plan has more than a handful of steps, split the story.

Test first

Ask for failing tests from the criteria, review them, then ask for the implementation.

Point, don’t paste

Name files and patterns to follow rather than pasting large blocks of code.

Stop points

“Plan first”, “ask before adding dependencies”, “stop if tests need changing”.

Course-correct

Interrupt early when it drifts. Two failed corrections? /clear and restart with a better spec.

Capture lessons

Repeated correction? Put it in CLAUDE.md or a skill, so it never needs saying again.

These habits come from daily use. The most underrated is restarting: a session full of failed attempts tends to repeat them, and a fresh session with a sharper spec is usually faster.

The last card closes the loop with Modules 2 and 3: every correction you make twice should become project memory.

Tools and integration

Connect agents to your work items, browsers and pipelines.

Module 5 widens the agent’s reach beyond the repo: MCP servers for external systems, hooks for automatic checks, and headless mode for CI.

Module 5 · MCP

MCP: plug in external tools

.mcp.json · shared with the team
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    },
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    }
  }
}
terminal
claude mcp add --scope project playwright -- npx @playwright/mcp@latest
claude mcp list

Useful servers

  • Azure DevOps — read stories and criteria, update work items
  • GitHub — issues, PRs and reviews
  • Playwright — drive a real browser to explore and test

Each server is code with your credentials. Install only trusted servers, least privilege.

MCP, the Model Context Protocol, is an open standard for connecting agents to tools. A project-scoped .mcp.json is committed so the whole team gets the same tools.

Treat MCP servers like any dependency: vet the source, pin versions where you can, and give them the narrowest access that works. Content they return, such as web pages or tickets, can contain prompt injection.

Module 5 · Hooks

Hooks: checks that always run

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command",
        "command": "npx prettier --write ." }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": ".claude/hooks/block-risky.sh" }]
    }]
  }
}

How they work

  • Shell commands run on events such as PreToolUse, PostToolUse, UserPromptSubmit, Stop
  • A PreToolUse hook that exits with code 2 blocks the action and tells the agent why
  • Deterministic: they run every time, unlike instructions the agent might skip

CLAUDE.md is guidance; hooks are enforcement. If something must always happen, such as formatting or blocking pushes to main, make it a hook.

The block script receives the proposed command as JSON on standard input and can reject it with exit code 2 and a message.

Module 5 · Automation

Headless mode in a pipeline

azure-pipelines.yml · PR triage step
- script: |
    claude -p "Review this PR's diff against main. List
      risks ranked by severity with file:line. Do not
      edit files." \
      --permission-mode dontAsk \
      --allowedTools "Read Grep Glob Bash(git diff *)" \
      --output-format json \
      --max-budget-usd 2 > review.json
  displayName: Agent review (advisory)
  env:
    ANTHROPIC_API_KEY: $(ANTHROPIC_API_KEY)  # secret variable

Patterns

  • Advisory first: post findings; don’t block merges on agent output
  • Strict allow list with dontAsk: anything else is denied
  • Budget cap per run with --max-budget-usd
  • Structured output with --output-format json

Every flag here is from the current claude --help; check your version, as the CLI evolves quickly. GitHub users can use the official Claude Code GitHub Action instead of a script step.

Start with agent review as advice to a human reviewer. Only consider gating on it once you trust its signal on your codebase.

06

Quality and guardrails

Trust, but verify: tests, reviews, sign-off and governance.

Module 6 is what makes agentic coding acceptable to a security team or an auditor. Speed is only useful if the output is trustworthy.

Module 6 · Quality

Every change, the same path

StoryAMP criteria
BranchAgent builds with tests
Agent reviewReviewer and security checks
CIBuild, tests, scans
Human reviewApproves the PR
MergeBranch policy enforced

Same bar as people: agent code goes through the same branch policies, required reviewers and CI as human code. No side doors.

Watch the tests: an agent may “fix” a failing test by weakening it. Review test changes as closely as code.

The principle is simple: no special treatment. Agent-authored changes meet the same Definition of Done.

The pitfall is real and common. If a test file changes in the same PR as the code it tests, look closely at why.

Module 6 · Guardrails

Risks and the controls that cover them

RiskControl
Secrets leak into prompts or commitsDeny reads of .env*; Key Vault; secret scanning in CI
Destructive commandsDeny rules and PreToolUse hooks; risky work in containers or VMs
Prompt injection from web pages, tickets, MCPLeast-privilege tools; human approval for anything external
Plausible but wrong codeTests from criteria; agent review; required human reviewer
Scope creep and unrequested changesPlan mode; small stories; review the full diff
Runaway costBudget caps in CI; usage dashboards; right model per task
Unvetted dependencies“Ask before adding dependencies” rule; dependency scanning

No single control is enough; the layers together make the risk acceptable. Notice that most controls are things good teams already do: branch policies, secret scanning, code review.

Prompt injection deserves a moment: anything the agent reads can contain instructions, so limit what it can do after reading untrusted content.

Module 6 · Governance

Data governance in regulated sectors

Data
  • Sample data only in prompts, fixtures and tests
  • No personal, patient or confidential data unless explicitly approved
  • Synthetic data generators for realistic test sets
Platform
  • Enterprise or team plans with agreed data-use terms
  • Cloud-hosted options, e.g. via Azure, for data residency needs
  • Single sign-on and managed settings for central policy
Process
  • A short AI use policy: what is allowed, where
  • Data protection impact assessment where required
  • PRs record that agents were used, for audit
People
  • A named human is accountable for every merge
  • Training before access, like any production tool
  • Regular review of what agents are allowed to do

For regulated organisations, governance is what unlocks adoption rather than what blocks it. Agree the policy up front and agentic coding becomes a normal, auditable tool.

Check provider terms and your own information governance team’s requirements; this slide is a starting checklist, not legal advice.

Hands-on lab · Part 1

Set up and specify

  1. Clone the sample repo, create a branch lab/<your-name>, start claudeA session in the repo root
  2. Run /init, then add three rules: tests required, no .env access, sample data onlyA short CLAUDE.md you would be happy to commit

Walk the room during step 4: weak criteria here cause most of the trouble later.

Hands-on lab · Part 2

Build, review and merge

  1. In plan mode, give the agent your story and criteria; review and adjust the planA plan that names the tests it will write
  2. Switch to acceptEdits and let it implement, tests firstTests fail first, then pass; lint and typecheck clean
  3. Run the read-only reviewer agent on your branchFindings ranked by severity; fix or justify each one
  4. Ask the agent to open the PR using your create-pr skillA PR with what, why and how tested
  5. Swap with your partner: review their PR, comment, approve, mergeA merged PR, approved by a human who didn’t write it

The partner review is the important bit. Ask reviewers to check the tests as hard as the code, and to look for anything the agent changed that the story did not ask for.

If time is short, stop after step 4 and do the reviews together on screen.

Flight rules

Guardrails that speed you up

  • People are accountable — a human approves every merge
  • Spec before code — AMP criteria, then plan mode
  • Tests are the agent’s eyes — no tests, no agent
  • Same bar as humans — branch policies, CI, reviews
  • Memory as code — CLAUDE.md, skills and settings in Git
  • Enforce with hooks, guide with instructions
  • Least privilege — tools, MCP servers and permissions
  • Sample data only unless explicitly approved
  • Small stories — one story, one session, one PR
  • Budget and measure — cost caps and usage reviews
