Why it matters

The hardest decision to undo

Screens can be rebuilt in a sprint. Data outlives every app built on top of it.

  • The store fixes your security model, scale ceiling and licence bill
  • Migrating later means re-keying relationships, re-building permissions and re-testing every app
  • Most “Power Apps is slow” complaints are really data and delegation problems
  • There is no single right answer — only the right store for each kind of data

The classic trap: “We’ll start on a SharePoint list and move later.” Later rarely comes — the list just grows.

Today’s goal: a repeatable way to choose, with the trade-offs written down.

Set the scene: the user interface is cheap to change, the data model is not. Once records, relationships and permissions exist, moving them is a project in its own right.

Ask the room for a story of a SharePoint list that outgrew itself — there is almost always one.

The contenders

Three stores at a glance

Dataverse

Business data platform
  • Relational tables with rich types
  • Role-based security built in
  • Native to model-driven apps and solutions

SharePoint

Documents and simple lists
  • Already licensed with Microsoft 365
  • Great for documents and metadata
  • Flat lists, limited relationships

Azure SQL

Full relational engine
  • T-SQL, views, stored procedures
  • Scales to very large volumes
  • Shared by apps, APIs and reporting

One-line positioning for each. Dataverse is a managed business data platform; SharePoint is a collaboration platform that happens to store lists; Azure SQL is a general-purpose relational database.

We will come back to this as a full decision matrix in module 6.

01

Dataverse

Tables, relationships and logic — the data platform under Power Platform and Dynamics 365.

Module one: how Dataverse models data. We cover table types, relationships, column types and business logic, then look at the Web API.

Module 1 · Dataverse

Four kinds of table

TypeWhat it isUse it for
StandardRelational table in Dataverse, user- or organisation-ownedMost business records: requests, assets, cases
ActivityStandard table with time and party fields; appears on timelinesEmails, calls, appointments, custom interactions
ElasticBacked by Azure Cosmos DB; scales horizontally, fewer relational featuresHigh-volume telemetry, logs, IoT readings
VirtualRows live in an external system; Dataverse holds no dataSurfacing SQL or other data without copying it

Ownership is set at creation: choose user/team-owned if you will ever need row-level security — it can’t be changed later.

Standard tables cover ninety per cent of needs. Elastic tables trade relational features for scale; virtual tables let model-driven apps show external data in place.

Stress the ownership point: organisation-owned tables can’t restrict rows by owner or business unit, and you cannot switch later.

Module 1 · Dataverse

Relationships and cascade behaviour

Site1 site…
Asset…has many assets (1:N)
Service request…each with many requests
TagRequests ↔ tags (N:N)
  • 1:N / N:1 — a lookup column on the child table
  • N:N — native (hidden intersect table) or manual (your own table, so you can add columns)
  • Parental — delete, assign and share cascade to children
  • Referential — children stay; choose Remove link or Restrict on delete

Walk the sample model we will use in the lab: sites, assets, service requests and tags.

Cascade behaviour is where surprises happen. A parental relationship means deleting a site deletes its assets, and reassigning a site reassigns them too. Restrict delete is often the safer default for reference data.

Module 1 · Dataverse

Columns that carry logic

  • Choice / choices — prefer global choices for values shared across tables
  • Formula columns — Power Fx, calculated when read
  • Rollup columns — aggregate child rows on a schedule (not real-time)
  • Business rules — simple validation and defaults, no code
  • Plug-ins and flows — when the logic outgrows the above
Formula column · kai_daysopen
// Whole days since the request was raised
DateDiff('Created On', UTCNow(), TimeUnit.Days)
Formula column · kai_isoverdue
If(
  Status = 'Status (Requests)'.Open
    && 'Due Date' < UTCToday(),
  true, false
)

Pitfall: filtering or sorting on time-based formula columns can be limited — test views and delegation early.

Formula columns use Power Fx, so makers already know the language. They are evaluated at read time, so they are always current but have some restrictions on sorting and filtering.

Rollups run on a schedule, by default every few hours, so do not use them for anything that must be exact right now.

Module 1 · Dataverse

Querying from code: OData and FetchXML

Web API (OData v4)
GET https://{org}.crm11.dynamics.com
  /api/data/v9.2/kai_assets
  ?$select=kai_name,kai_status,createdon
  &$filter=kai_status eq 1
     and contains(kai_name,'pump')
  &$expand=kai_SiteId($select=kai_name)
  &$orderby=createdon desc
  &$top=50

Authorization: Bearer {entra-token}
Prefer: odata.include-annotations="*"
FetchXML
<fetch top="50">
  <entity name="kai_asset">
    <attribute name="kai_name" />
    <attribute name="kai_status" />
    <attribute name="createdon" />
    <order attribute="createdon" descending="true" />
    <filter>
      <condition attribute="kai_status"
                 operator="eq" value="1" />
      <condition attribute="kai_name"
                 operator="like" value="%pump%" />
    </filter>
    <link-entity name="kai_site"
        from="kai_siteid" to="kai_siteid">
      <attribute name="kai_name" />
    </link-entity>
  </entity>
</fetch>

Both return the same rows. OData suits apps and APIs; FetchXML suits views, reports and aggregates. The host name depends on your region.

Everything in Dataverse is reachable through the Web API with an Entra ID token, so custom code, Azure Functions and integrations all use the same security model as the apps.

Point out $select: always ask for only the columns you need. FetchXML supports aggregates and is what views use under the hood.

Module 1 · Dataverse

Get the schema right first time

Build inside a solution with your own publisher prefix (e.g. kai_), never the default cr123_.

Name tables in the singular and write a description for every column — it is your data dictionary.

Use alternate keys for anything you import or integrate, so upserts don’t create duplicates.

Schema names are permanent. You can rename the display name, never the logical name.

Text column lengths can be increased but are awkward to reduce once data exists.

Don’t mirror a spreadsheet. Normalise repeating columns into child tables.

These are the mistakes we see most on inherited Dataverse environments. The publisher prefix ends up in every logical name, every API call and every integration, so it is worth getting right on day one.

Alternate keys are the unsung hero of data migration: they let you re-run an import safely.

02

Dataverse security

Business units, roles, teams and columns — who sees which rows, and which fields.

Module two: the Dataverse security model. This is the biggest reason to choose Dataverse over SharePoint, so it is worth understanding properly.

Module 2 · Security

How the pieces fit

User or Entra groupSigns in with Entra ID
TeamOwner team or Entra group team
Security rolePrivileges × depth per table
Business unitBoundary for “my unit’s” rows
RowsCreate, read, write, delete, append, share…
  • Roles are additive — a user gets the union of every role they hold, directly or via teams
  • Entra group teams let IT manage membership in one place
  • Business units mirror who should see whose data, not the org chart
  • Environment access is gated by an Entra security group first

Read it left to right: a person belongs to teams, teams and people hold roles, roles grant privileges to a depth, and depth is measured against business units.

Recommend Entra group teams so joiners and leavers are handled in Entra, not by hand in Dataverse. And always restrict each environment to a security group.

Module 2 · Security

Privilege depth: how far a role reaches

DepthThe user can act on rows…Typical role
NoneNo access to the tableAnyone outside the process
UserThey own, or that are shared with them or their teamsRequester
Business unitOwned by anyone in their business unitTeam lead
Parent: child BUIn their business unit and every unit below itRegional manager
OrganisationEvery row in the environmentAdministrator, reporting

Start from least privilege: copy a minimal role and add to it — never start from System Administrator and take away.

Each privilege — create, read, write, delete, append, append to, assign, share — gets its own depth per table. So a requester might create at user level but read at business-unit level.

Encourage people to design roles per persona and document them in a matrix before building them.

Module 2 · Security

Columns, sharing and auditing

Column security
  • Mark a column as secured
  • Grant read / update / create via a column security profile
  • Everyone else sees it locked, the value masked as ********
Record sharing
  • Grants access to one row for one user or team
  • Fine for exceptions
  • Slow and opaque at volume
Auditing
  • Enable at environment, table and column level
  • Records who changed what, and when
  • Audit logs use log capacity — set retention

Pitfall: using sharing as the main security model. If you share thousands of rows, redesign with business units or owner teams instead.

Column security hides sensitive fields such as personal identifiers from people who can otherwise see the row. Sharing is for genuine exceptions; at scale it slows queries and becomes impossible to reason about.

Auditing is not on by default for every table. Agree what needs auditing and for how long as part of the design.

03

SharePoint lists and libraries

Brilliant for documents and simple lists — as long as you know where the edges are.

Module three: SharePoint. It is everywhere and already licensed, which is exactly why it gets stretched beyond what it is good at.

Module 3 · SharePoint

When SharePoint is the right call

Good fit

  • Documents with metadata, versioning and co-authoring
  • Simple lists: a few thousand rows, few relationships
  • Team-level data where site permissions are enough
  • Standard-licence apps and flows for Microsoft 365 users

Poor fit

  • Data that needs row-level security
  • Many related lists and complex lookups
  • Lists heading for tens of thousands of rows
  • Transactions, integrity rules or heavy reporting

A common hybrid: structured records in Dataverse or SQL, with their documents in a SharePoint library.

SharePoint is not the enemy; it is the best place for documents. The problems start when lists are used as a relational database.

The hybrid pattern is very common: Dataverse has built-in SharePoint document integration for exactly this reason.

Module 3 · SharePoint

The 5,000-item threshold and indexes

  • A list can hold millions of items, but a query that scans more than 5,000 is blocked
  • The threshold can’t be raised in SharePoint Online
  • Index the columns you filter and sort on — ideally before the list passes 5,000
  • The first filter in a query must use an indexed column and cut results below 5,000
  • Lookups, people and managed metadata columns add joins — keep each view to a few
Power Fx · filter on indexed columns
// Status and Site are indexed
Filter(
  Assets,
  Status.Value = "Active",
  SiteCode = drpSite.Selected.Code
)

Pitfall: adding an index to a list that is already over the threshold can fail — plan indexes on day one.

The 5,000 list view threshold is the single most common SharePoint surprise. It limits how many items a single query can scan, not how many the list can store.

Indexes and selective first filters are the fix. If you can’t design queries that stay under the threshold, that is a strong signal to use Dataverse or SQL.

Module 3 · SharePoint

Permission inheritance, and why item-level hurts

  • SiteOwners, members, visitors
  • ListInherits from the site
  • ItemUnique permissions = broken inheritance
  • LibraryInherits from the site
  • FolderBreak here, not on every file
  • Every broken item creates its own permission scope to manage and audit
  • Many unique scopes in one list slow queries and become impossible to reason about
  • Power Apps still lists what a user can read — hiding data in the app is not security
  • Need per-row access? That is a Dataverse or SQL requirement

SharePoint security is designed around sites, lists and libraries. Breaking inheritance per item works for a handful of exceptions but does not scale.

Make the point firmly: filtering a gallery in Power Apps is not security. Anyone with list access can open the list directly or call the API.

04

Azure SQL

A full relational engine — when you need scale, T-SQL or one database shared by many systems.

Module four: Azure SQL Database. We cover service tiers, identity, network isolation, row-level security and backups.

Module 4 · Azure SQL

Purchasing models and tiers

OptionHow it’s sizedGood for
DTU (Basic / Standard / Premium)Bundled compute, storage and I/OSmall, steady, simple workloads
vCore · General PurposeChoose vCores and storage separatelyMost business applications
vCore · ServerlessAuto-scales; can auto-pause when idleDev/test and intermittent apps
vCore · Business CriticalLocal SSD, built-in replicasLow latency, high availability
vCore · HyperscaleStorage scales independently, very large databasesLarge and fast-growing data
Elastic poolMany databases share one poolMany small databases, uneven load

Start small and scale: you can move between most tiers online. Watch for the first-connection delay after a serverless database auto-pauses.

vCore is the recommended model for new work because you can see and size compute and storage independently, and use Azure Hybrid Benefit if you have SQL licences.

Serverless is ideal for labs and quiet apps, but the resume delay after auto-pause surprises users — turn auto-pause off for interactive production apps.

Module 4 · Azure SQL

No passwords, no public endpoint

App or FunctionSystem-assigned managed identity
Entra IDIssues the access token
Private endpointPrivate IP in your VNet
Azure SQLEntra-only auth, public access off
  • Turn on Microsoft Entra-only authentication
  • Grant groups and identities, not people
T-SQL · grant a managed identity
CREATE USER [app-assets-prod] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [app-assets-prod];
ALTER ROLE db_datawriter ADD MEMBER [app-assets-prod];

The target pattern: no SQL logins, no connection-string passwords. The app authenticates with its managed identity, and the database is reachable only through a private endpoint.

Power Platform can reach a private database through an on-premises data gateway or Power Platform virtual network support. Plan this early: it affects licensing and environment setup.

Module 4 · Azure SQL

Row-level security in the engine

rls.sql
CREATE FUNCTION sec.fn_SiteFilter(@SiteId int)
  RETURNS TABLE WITH SCHEMABINDING AS
RETURN
  SELECT 1 AS allowed
  FROM dbo.UserSite us
  WHERE us.SiteId = @SiteId
    AND us.UserName = USER_NAME();
GO
CREATE SECURITY POLICY sec.SitePolicy
  ADD FILTER PREDICATE sec.fn_SiteFilter(SiteId)
    ON dbo.Asset,
  ADD BLOCK PREDICATE sec.fn_SiteFilter(SiteId)
    ON dbo.Asset AFTER INSERT,
  ADD BLOCK PREDICATE sec.fn_SiteFilter(SiteId)
    ON dbo.Asset AFTER UPDATE
  WITH (STATE = ON);

What to notice

  • Filter predicate hides rows on read
  • Block predicates stop inserts into other sites, and updates that move a row to one
  • Applies to every client: apps, APIs, reports
  • Index the predicate columns

A shared service identity is one user to SQL. Pass the real user with SESSION_CONTEXT or Entra delegation.

Row-level security puts the rule in the database, so it cannot be bypassed by a different client. The predicate function decides which rows each user may see.

The catch: if every request arrives as one service identity, SQL cannot tell users apart. Either connect as the signed-in user or set SESSION_CONTEXT from a trusted API and filter on that.

Module 4 · Azure SQL

Backups, and connecting from Power Platform

Backups
  • Automatic full, differential and log backups
  • Point-in-time restore within a configurable window (default 7 days)
  • Long-term retention for weekly, monthly or yearly copies
  • Restores create a new database — rehearse the swap
From Power Platform
  • SQL Server connector is premium
  • Use Entra ID authentication, not SQL logins
  • Private databases need a data gateway or VNet support
  • Use views for reads and stored procedures for complex writes

Virtual tables can surface SQL rows inside Dataverse and model-driven apps without copying data.

Backups are on by default, but a restore is only proven once you have done one. Rehearse it in test, including repointing the app.

For Power Apps, views keep delegation simple and stored procedures (called from flows or APIs) handle multi-table writes in a transaction.

05

Delegation, scale and performance

Why the app shows 500 rows when there are 50,000 — and how to fix it.

Welcome back from the break. Module five is the one that explains most “missing data” bugs in Power Apps: delegation.

Module 5 · Delegation

Who does the filtering?

Delegable

AppSends the query
Data sourceFilters all rows
Correct resultsPaged back

Not delegable

Data sourceReturns first 500
AppFilters locally
Silently wrongRows 501+ ignored
  • The data row limit is 500 by default and can be raised to 2,000 in app settings — a test aid, not a fix
  • Studio flags it with a delegation warning (blue underline) — treat warnings as bugs

Delegation means pushing the work to the data source. When a formula can’t be delegated, Power Apps fetches only the first 500 (or up to 2,000) rows and works on those, so results are silently incomplete once the data grows.

Tip for testing: set the limit to a tiny number like 5 in development so problems show up immediately.

Module 5 · Delegation

Rewrite the formula, not the limit

✗ Not delegable
// Function on the column
Filter(Assets,
  Year(PurchaseDate) = 2026)

// Search on SharePoint
Search(Assets, txtFind.Text, "Title")

// Substring on SharePoint
Filter(Assets,
  txtFind.Text in Title)
✓ Delegable rewrite
// Compare the raw column to a range
Filter(Assets,
  PurchaseDate >= Date(2026,1,1),
  PurchaseDate < Date(2027,1,1))

// Prefix match instead of search
Filter(Assets,
  StartsWith(Title, txtFind.Text))

// Or move it to Dataverse / SQL,
// where Search and in can delegate

Rule of thumb: keep the column bare on the left; put functions on the value you compare it with.

The commonest cause of a delegation warning is wrapping the column in a function such as Year, Lower or Len. The source can’t evaluate that, so Power Apps falls back to local processing.

Rewrite to compare the bare column against a computed value. For free-text search on large SharePoint lists, StartsWith is often the best you can do.

Module 5 · Delegation

Same formula, different source

Formula patternDataverseSharePointAzure SQL
Filter with =, <, > on a columnYesYesYes
StartsWithYesYesYes
Search / in (substring)YesNoYes
Sort / SortByColumns on a columnYesSimple columnsYes
Function on the column (Year, Lower, Len)NoNoNo

Delegation support changes between releases and by column type — always check the current connector documentation and trust the warning in Studio.

This is a simplified view for the common cases. The details depend on column type: for example, SharePoint lookups and person columns have more restrictions.

The practical message: Dataverse and SQL delegate far more than SharePoint, which is another reason large or search-heavy data shouldn’t live in a list.

Module 5 · Scale

Limits, throttling and retries

Dataverse
  • Service protection limits per user, per server, over a 5-minute window: request count, execution time and concurrency
  • Plus Power Platform request entitlements per licence
SharePoint
  • Tenant and app throttling under heavy load
  • Bulk loops in flows hit it first
  • Batch requests and use delta queries
Azure SQL
  • Bound by the tier’s compute, I/O and session limits
  • Watch Query Performance Insight
  • Index for your real queries

Always honour 429 and Retry-After. Integrations that retry instantly make throttling worse. Batch, page and back off.

Every store protects itself. Dataverse service protection limits are evaluated per user over a sliding five-minute window, covering number of requests, total execution time and concurrent requests; exceed them and you receive a 429 with a Retry-After header.

Check the current numbers in Microsoft Learn before quoting them — they and the licence-based request entitlements have changed over time.

Licensing, cost and choosing

Putting it together: a repeatable way to pick the right store for each kind of data.

Module six brings everything together into a decision matrix and a simple decision flow you can reuse on your own projects.

Module 6 · Licensing

Price the whole solution, not the store: once one premium connector is in the app, every user needs a premium licence anyway.

Licensing is often the deciding factor, so cover it honestly. SharePoint looks free because it is in Microsoft 365, but the moment an app also uses SQL or Dataverse, users need premium licences regardless.

Do not quote prices from this slide: check current Microsoft pricing and your agreement, as entitlements and capacity allowances change.

Module 6 · Choosing

Very large, shared or needs T-SQL?Yes → Azure SQL

Ask the questions in this order and stop at the first yes. It is deliberately simple: the matrix is for the detailed comparison, this is for the first conversation.

Recording the decision matters as much as making it, so the next team knows why and when to revisit.

Flight rules

Rules that save you a migration

  • Choose per kind of data, not per project — hybrids are normal
  • Decide security first — if you need row-level access, rule SharePoint lists out
  • Treat delegation warnings as bugs and test with a tiny row limit
  • Index before you import on SharePoint; index for real queries on SQL
  • Build Dataverse inside a solution with your own publisher prefix
  • No passwords — Entra ID and managed identities everywhere
  • Price the whole solution, including licences and capacity
  • Record the decision and what would make you revisit it
