Rule of thumb: data-heavy back office → model-driven. Task-focused or mobile → canvas. Outgrowing Power Fx, or you have React developers → Code App.

Walk the table row by row. The key trade-off is control versus speed: model-driven is fastest for data-centric apps, Code Apps give total control but need developers.

Mixing is normal: a model-driven back office for staff plus a canvas or Code App for a focused task. Licensing changes regularly, so always check the current licensing guide before committing.

Module 2 · Canvas apps

Canvas apps done properly

Declarative Power Fx
  • Named formulas in App.Formulas instead of a long OnStart
  • User-defined functions: write a business rule once, reuse it
  • With() for local names, not global variables
  • Keep Set() for real state, such as the selected record
Fast, reusable and accessible
  • StartScreen, Concurrent() and ShowColumns for quick loads
  • Components with custom properties, shared from a library
  • Accessible labels, keyboard tab order and 4.5 : 1 contrast
  • Run App Checker and Monitor before every release

Delegation: a non-delegable query pulls the first 500 rows (max 2,000) and filters locally. No error, just missing data — treat the yellow triangle as a build failure.

One slide for the whole module; the detail comes in the demo. The theme is declarative Power Fx: say what a value is once, and let the platform work out when to calculate it.

Named formulas are evaluated lazily and never go stale, unlike collections loaded in OnStart. User-defined functions give typed, reusable business rules.

Delegation is the number-one cause of “it worked in testing” bugs: the app silently works on part of the data. Delegation support varies by connector, which is a big factor in choosing a data store (W-T2).

Module 3 · Anatomy

Data first, then the app

TablesColumns, relationships, choices
Forms and viewsMain, quick create, quick view
Business process flowsGuided stages
App and sitemapNavigation and areas
Security rolesWho sees which rows

Design the data model on a whiteboard first: tables, relationships, ownership (user or team) and which columns are required.

Changing a table’s ownership type or a column’s data type after go-live is painful or impossible.

Walk left to right. Tables are where the real design work happens; forms, views and the app itself are mostly configuration.

Security roles are row-level: user-owned or team-owned tables plus business units decide who sees what. Get ownership right on day one.

Where rules live matters: business rules for simple show, hide and require; Power Automate for notifications and integrations; a plug-in for validation that must never be bypassed, whichever way the data arrives.

Module 4 · Code Apps

Pro-code UI, managed platform

Your appReact or Vue, TypeScript, Vite
Client library@microsoft/power-apps + generated services
Connectors and Dataverse1,500+ connectors from JavaScript
The platform gives you
  • Entra ID sign-in — no auth code to write
  • Hosting, sharing limits, DLP and Conditional Access
  • Solutions for ALM; health metrics in the admin centre
Before you start
  • Admin turns on Enable code apps per environment
  • Node.js LTS, Git and the Power Apps CLI
  • End users need Power Apps Premium (or pay-as-you-go)

A Code App is a normal single-page app. The difference is that it is published to and run by Power Platform, which handles identity, connections and governance.

The inner loop is four Power Apps CLI commands: pa app init, pa app add data-source, pa app run and pa app push. Preview-era projects used pac code …; the concepts are the same.

Source lives in your own Git repo, and pa app push --solution-id puts the app in a solution, so it deploys like everything else. Check the Microsoft Learn limitations page before each project; the list is shrinking fast.

The environment setting lives in the admin centre under Settings, Product, Features. End users need Power Apps Premium, which matters for the business case.

Module 5 · Error handling

Try / catch / finally with scopes

Scope: Try
Get row
Call API
Update row

Runs normally

Scope: Catch
Filter failed actions
Alert the team
Set varFailed = true

Run after Try: has failed, has timed out

Scope: Finally
Log the run
Release lock
If varFailed: Terminate: Failed

Run after Catch: all four outcomes

Without Terminate: Failed, a handled error shows as Succeeded in run history. Put it last: nothing runs after Terminate, so in Catch it would skip Finally.

Scopes plus “Configure run after” give you structured error handling. Catch only runs when Try fails or times out; Finally runs whatever happens.

Terminate ends the run on the spot, and no action after it runs, not even one set to run after failure. So Catch only records the failure in a variable, and the last action in Finally terminates the run as Failed when that variable is set. Logging and releasing the lock always happen first.

Note that Finally is set to run after Catch with all outcomes ticked, including skipped, otherwise it won’t run on the happy path.

Mention reuse and throughput briefly: child flows for shared logic, concurrency on triggers and loops, retry policy set to none for calls that must not repeat, and pagination on List rows.

Module 6 · ALM

Package it, govern it, move it safely

DevUnmanaged; makers build here
Source controlpac solution unpack into Git
TestManaged import + settings
ProdManaged, approval gate
Solutions
  • Everything in a solution with your own publisher prefix
  • Unmanaged in dev, managed everywhere else
  • Environment variables instead of hard-coded values
  • Connection references, bound per environment
Connectors and DLP
  • Business, non-business and blocked groups
  • An app or flow can’t mix business and non-business
  • Lock down the default environment hardest
  • Premium and custom connectors drive licensing

Everything built today is only valuable if it can move safely from dev to test to production. Solutions are the unit of deployment; managed solutions give clean upgrades and clean removal.

Agree the publisher prefix as a team on day one: it appears in every table and column name forever. Environment variables replace URLs, site IDs, e-mail addresses and thresholds; secret variables read from Azure Key Vault.

DLP policies stop business data flowing into non-business services. No DevOps team? Pipelines in Power Platform deploy from the maker portal with approvals. Full CI/CD with Azure DevOps is W-T4.

Recap

Flight rules, and where next

  • Pick the app type from the problem, not habit
  • Never build in the default environment
  • Everything in a solution, with your own publisher
  • No hard-coded values — variables and references
  • Managed only outside dev; never edit in test or prod
  • Delegation warnings are build failures
  • Every flow has try / catch / finally and alerts
  • Code Apps: never hand-edit generated/
