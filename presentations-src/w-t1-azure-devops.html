Why it matters

One source of truth, or many sources of noise

Common anti-patterns
  • Work tracked in spreadsheets, email and chat — the board is out of date by Tuesday
  • One giant backlog with no epics or features, so nobody can see progress
  • Stories with no acceptance criteria: “done” means “I stopped typing”
  • Direct pushes to main, no reviews, no link from code to work
  • Manual status reports rebuilt every week
What good looks like
  • Every piece of work is a work item, in a clear hierarchy
  • Boards reflect reality, with WIP limits that expose bottlenecks
  • Testable acceptance criteria, linked to test cases
  • Every change goes through a PR linked to a story
  • Dashboards and queries replace status meetings

Ask which of the anti-patterns people recognise. Most teams have at least two.

The message: Azure DevOps only helps if it is the single source of truth. Traceability from epic to story to commit to test to release is the real prize, and it costs very little once the habits are in place.

01

Organisation, projects and process

Get the structure right first: it is far harder to change once the work is in.

Module 1, about 20 minutes. We cover how an organisation is structured, which process to pick, the T-Minus-15 work item types and how area and iteration paths work.

Module 1 · Structure

How Azure DevOps is organised

  • Orgdev.azure.com/contoso
  • ProjectDelivery
  • TeamApps squad
  • TeamData squad
  • AreaDelivery\Apps
  • IterationDelivery\2026\Sprint 21
  • Organisation — billing, users, Entra ID connection, policies
  • Project — a security and process boundary; one process per project
  • Team — its own backlog, board and sprints, scoped by area paths
  • Iteration paths — the sprint calendar, shared across teams

Tip: prefer fewer, larger projects with many teams. Cross-project queries and reporting are harder.

Organisation at the top, connected to Entra ID for sign-in. A project is the boundary for process and permissions. Teams live inside projects and see work through area paths.

The common mistake is one project per application or per team. That fragments the backlog and makes portfolio views painful. Start with one project and use teams and area paths.

Module 1 · Process

Choosing a process

ProcessBacklog typesGood forWatch out
BasicEpic → Issue → TaskSmall teams starting outOutgrown quickly
AgileEpic → Feature → User Story → Task, BugMost product teamsGood default base
ScrumEpic → Feature → Product Backlog Item → TaskStrict Scrum teamsEffort, not story points
CMMIEpic → Feature → Requirement → TaskFormal, audited change controlHeavyweight
Inherited (custom)Your types, fields, states and rulesA house process such as T-Minus-15Changes apply to every project using it

You can’t edit the four system processes. Create an inherited process from one of them, customise that, then point projects at it.

The four system processes are locked. All customisation happens in an inherited process, which you derive from Basic, Agile, Scrum or CMMI.

Recommendation: inherit from Agile. It has the right backlog levels and story points. The T-Minus-15 process template is exactly that: an inherited Agile process with extra types and fields.

Hosted XML processes still exist for some legacy collections; avoid them for anything new.

Module 1 · T-Minus-15 process

The T-Minus-15 work item types

The backlog hierarchy

  • EpicLean business case, outcome, go/no-go
  • FeatureA shippable deliverable, MoSCoW priority
  • StoryUser value, AMP acceptance criteria
  • TaskHours of work to deliver the story
Plus the types that keep delivery honest
  • BugFails a story’s acceptance criteria
  • EnhancementAn improvement that doesn’t block acceptance
  • IssueA blocker or impediment, now
  • RiskSomething that might go wrong later
  • QuestionA clarification needed before work can proceed

This is the T-Minus-15 hierarchy. Epics carry the business case and are where you make go/no-go decisions. Features are deliverables with MoSCoW priority. Stories carry the acceptance criteria. Tasks are the hours.

The distinction between bug and enhancement matters: a bug means the story did not meet its acceptance criteria; an enhancement is an improvement that does not block acceptance. Issues, risks and questions keep blockers and unknowns visible on the board instead of hidden in email.

Module 1 · Acceptance criteria

AMP: Acceptance, Measure, Proof

User Story 1042 · Acceptance Criteria
# A · Acceptance (Gherkin)
SCENARIO: Add a new contact
GIVEN I am on the Add Contact screen
WHEN  I enter First Name "Jane", Last Name "Smith"
THEN  the contact is saved
AND   Display Name shows "Jane Smith"

# M · Measure
- Save completes within 2 seconds
- Zero validation errors on valid input

# P · Proof
- TC1: Add contact with valid data
- Playwright: contacts.spec.ts › add contact
  • A — testable scenarios in Gherkin
  • M — numbers: speed, accuracy, coverage
  • P — how we prove it: test case IDs, automated tests, screenshots

Criteria this precise can be handed to a tester, a developer or an AI agent without a meeting.

AMP is the T-Minus-15 format for acceptance criteria and it lives in the standard Acceptance Criteria field.

Acceptance is Gherkin, so it maps straight to test cases. Measure adds the numbers people usually forget. Proof says exactly how we will show it is done, which is what testers and reviewers need.

Point out that this precision is what makes agentic coding work too; see W-T5.

Module 1 · Areas and iterations

Set up the project from the command line

setup-project.sh
az extension add --name azure-devops
az devops configure --defaults \
  organization=https://dev.azure.com/contoso project=Delivery

# Project from an inherited process
az devops project create --name Delivery --process "T-Minus-15"

# Area paths: one per team or product area
az boards area project create --name Apps
az boards area project create --name Data

# Iterations: a two-week sprint
az boards iteration project create --name "Sprint 21" \
  --path "\Delivery\Iteration\2026" \
  --start-date 2026-11-16 --finish-date 2026-11-27
  • Areas = what: product, component or team
  • Iterations = when: release and sprint calendar
  • Each team picks its area paths and subscribes to iterations

Pitfall: using areas for status or people. Use states and the Assigned To field instead.

Everything in the UI can be scripted. That matters when you set up several projects or want a repeatable baseline.

Areas answer "what is this about"; iterations answer "when". Teams then select which areas they own and which iterations they work in, under Project settings, Team configuration.

If the iteration create command complains about the path, create the parent 2026 node first. Paths include the hidden Iteration root.

02

Backlogs and boards

A board people trust is the cheapest status report you’ll ever have.

Module 2, about 25 minutes: backlog levels, board configuration, WIP limits, Definition of Done, sprints and capacity, then a live demo.

Module 2 · Boards

A board that shows where work is stuck

NewCaptured, not ready
ReadyAMP criteria agreed
In progressWIP 4
Review / testWIP 3
DoneMeets the DoD
  • Columns map to states; add columns without changing the process
  • Split columns (Doing / Done) show work waiting to be pulled
  • WIP limits turn red when exceeded — stop starting, start finishing
  • Definition of Done per column, shown on the board
  • Swimlanes for an Expedite lane, not for people
  • Card styles and tag colours to flag blocked or overdue work

Board columns are configured per team and per backlog level, and map onto the process states. You can have more columns than states.

WIP limits are advisory in Azure DevOps: the column count turns red but nothing is blocked. That is fine; the point is to make the bottleneck visible and discuss it at stand-up.

Split columns help you see work that is finished in one stage but not yet pulled into the next, which is often where the real delay is.

Module 2 · Sprints

Sprints, capacity and burndown

Plan
  • Order the backlog by priority; drag stories into the sprint
  • Set capacity per person per day, and days off
  • Break stories into tasks with Remaining Work
  • Use Forecast with your velocity to see what fits
Track
  • Taskboard for daily stand-up
  • Sprint burndown on remaining work or story points
  • Velocity chart across the last sprints
  • Cumulative flow diagram to spot growing queues

Pitfall: a flat burndown usually means Remaining Work isn’t being updated, not that nobody is working. Make updating it part of stand-up.

Capacity planning is under the sprint's Capacity tab. Set hours per day per person and activity, and record days off; the capacity bars then turn red when someone is over-allocated.

Forecast on the backlog uses a velocity number you type in to draw lines showing which stories should fit in future sprints.

Encourage teams to update Remaining Work before stand-up. Without it the burndown is meaningless.

03

Queries and dashboards

Ask the data, don’t ask the team: replace status meetings with live views.

Module 3, about 20 minutes: WIQL, the three query types, charts, dashboards and Analytics for Power BI.

Module 3 · WIQL

Queries are just WIQL

Open stories in the current sprint
SELECT [System.Id], [System.Title],
       [System.State], [System.AssignedTo]
FROM   WorkItems
WHERE  [System.TeamProject] = @project
  AND  [System.WorkItemType] = 'User Story'
  AND  [System.State] <> 'Closed'
  AND  [System.IterationPath] = @CurrentIteration
  AND  [System.AreaPath] UNDER 'Delivery\Apps'
ORDER BY [Microsoft.VSTS.Common.BacklogPriority]
  • Macros: @Me, @Today - 7, @project, @CurrentIteration
  • UNDER includes child area or iteration paths
  • Save to Shared Queries so dashboards and alerts can use them

Build in the query editor; to see the WIQL text, use the WIQL Editor extension or fetch the query from the REST API.

Every query in the UI is WIQL underneath. The query editor doesn’t show the text, so install the WIQL Editor extension from the Marketplace, or fetch the saved query with the REST API (expand=wiql).

@CurrentIteration depends on team context, so in the API you may need the team-qualified form. @Today minus 7 is handy for "changed this week" queries.

Save team queries under Shared Queries in a folder per team; personal queries can't be used on dashboards.

Module 3 · Query types

Flat, direct links and tree queries

TypeUse it for
Flat listLists, charts, bulk edits
Direct linksStories with no test cases; bugs linked to a story
Tree of work itemsEpic → Feature → Story roll-ups and progress
Epic tree
SELECT [System.Id], [System.Title], [System.State]
FROM   WorkItemLinks
WHERE  ([Source].[System.WorkItemType] = 'Epic')
  AND  ([System.Links.LinkType] =
        'System.LinkTypes.Hierarchy-Forward')
  AND  ([Target].[System.State] <> 'Removed')
MODE   (Recursive)

Quality check query: a direct-links query for User Stories that do not have a Tested By link finds stories nobody has written tests for.

Three query types. Flat lists are the default. Direct links let you find work items with or without a particular link, which is great for quality checks. Tree queries show the hierarchy and are the basis for epic progress views.

Charts only work on flat queries; that catches people out.

Module 3 · Reporting

Dashboards and Analytics

Team dashboard widgets

  • Query tile and chart for work item queries
  • Sprint burndown and velocity
  • Cumulative flow, lead time and cycle time
  • Build history and test results trend
  • Markdown tile for the sprint goal
Analytics OData feed (Power BI)
GET https://analytics.dev.azure.com/
    contoso/Delivery/_odata/v4.0-preview/WorkItems
  ?$filter=WorkItemType eq 'User Story'
     and State ne 'Removed'
  &$select=WorkItemId,Title,State,StoryPoints
  &$expand=Iteration($select=IterationPath)

Dashboards for the team; Analytics views or OData + Power BI for portfolio and trend reporting.

Dashboards are per team or per project. Keep one dashboard per team with the sprint goal, burndown, a few query tiles and the build status.

For anything across projects or over long periods, use the Analytics service: Analytics views in Power BI, or OData queries directly. Always use $select and $filter; unfiltered OData queries are slow and can be throttled.

Test Plans

Every story is proved, not promised: from acceptance criteria to test runs.

Module 4, about 15 minutes: how plans, suites and cases are structured, and how they trace back to stories.

Module 4 · Structure

Plans, suites and cases

  • PlanSprint 21 test plan
  • SuiteStory 1042 · Add contact
  • CaseTC1 Add contact with valid data
  • CaseTC2 Reject invalid email
  • SharedShared steps: sign in
Suite typeContains
Requirement-basedCases linked to one story; results roll up to it
Query-basedCases matching a query, e.g. priority 1
StaticA hand-picked folder, e.g. regression

Turn each AMP scenario into a test case and each Proof line into a test case ID. Use shared steps for sign-in and other common setup.

One test plan per sprint or per release. Requirement-based suites are the most useful: one per story, so test results show up on the story itself.

Query-based suites are great for smoke or priority-1 regression packs that update themselves. Shared steps and parameters avoid duplicating the same steps across dozens of cases.

Module 4 · Traceability

From story to test run to bug

User StoryAMP criteria
Test caseTested By link
Test runManual or automated
BugCreated from the failed step
RetestStory accepted
  • The Test Runner records pass or fail per step, with screenshots and notes
  • A bug raised from a failed step carries the repro steps and links back to the story
  • Automated tests from a pipeline can be associated with test cases, so results appear in the plan
  • The Progress report shows pass rate per suite

Creating and managing test plans needs the Basic + Test Plans access level. Check licences before the team relies on it.

This is the traceability chain auditors and product owners care about. The story links to test cases via Tested By; runs record results; bugs created from a failed step carry the repro steps automatically.

Licensing: full test management needs Basic plus Test Plans. Stakeholders and Basic users can still run tests and give feedback, but check the current licensing page before promising anything.

05

Repos and pull requests

Short branches, protected main, and every change linked to the work it delivers.

Module 5, about 25 minutes: branching strategy, branch policies, PR templates and work item linking, then a live demo.

Module 5 · Branching

Release Flow branching

Topic branchusers/jo/1042-add-contact
Pull requestPolicies, review, build
mainAlways releasable
releases/2026.11Cut per release
  • Topic branches live for days, not weeks
  • All PRs target main; no long-lived develop branch
  • Hotfix: fix in main first, then cherry-pick to the release branch
  • Feature flags hide unfinished work instead of long branches

Release Flow is how Microsoft runs Azure DevOps itself: trunk-based development with short topic branches and release branches cut when you ship.

The key rule for hotfixes is "main first, then cherry-pick". That way a fix is never lost in the next release. Azure Repos has a cherry-pick button on completed PRs to make this easy.

Compare with GitFlow briefly if asked; the W-M6 Operate workshop covers branching strategy in more depth.

Module 5 · Branch policies

Lock down main with policies

PolicyWhyRecommended
Minimum number of reviewersFour eyes on every change2 (1 for small teams); reset votes on new pushes
Check for linked work itemsTraceability to the storyRequired
Check for comment resolutionNo review comment left hangingRequired
Limit merge typesA readable historySquash merge
Build validationMain never breaksRequired, expires on new pushes
Automatically included reviewersOwners review their codeBy path, e.g. /infra/* → platform team

These are the policies we turn on for every repo. Once any policy is on, direct pushes to main are blocked and everything goes through a PR.

Reset votes on new pushes, so an approval can't be reused after code changes. Squash merge keeps one commit per PR on main, which makes history and cherry-picks clean.

Path-based required reviewers act like a CODEOWNERS file: infra changes need the platform team, and so on.

Module 5 · Policies as code

Apply the same policies to every repo

protect-main.sh
REPO_ID=$(az repos show --repository web-app --query id -o tsv)

az repos policy approver-count create --repository-id $REPO_ID --branch main \
  --minimum-approver-count 2 --creator-vote-counts false --allow-downvotes false \
  --reset-on-source-push true --blocking true --enabled true

az repos policy work-item-linking create --repository-id $REPO_ID --branch main \
  --blocking true --enabled true

az repos policy comment-required create --repository-id $REPO_ID --branch main \
  --blocking true --enabled true

az repos policy merge-strategy create --repository-id $REPO_ID --branch main \
  --allow-squash true --blocking true --enabled true

az repos policy build create --repository-id $REPO_ID --branch main \
  --build-definition-id 12 --display-name "PR build" --queue-on-source-update-only true \
  --manual-queue-only false --valid-duration 720 --blocking true --enabled true

The same policies, scripted. Run this for every new repo so nobody has to remember the settings, or loop over all repos in a project.

Policies can also be set at project level for all repositories, under Project settings, Repositories, Policies. Script it when you need consistency across many projects.

Check flag names against the current az devops extension with --help before relying on them; the extension changes occasionally.

Module 5 · Pull requests

PR templates and work item links

.azuredevops/pull_request_template.md
## What and why
<!-- One or two sentences -->

## Work items
Fixes #1042

## How to test
1. ...

## Checklist
- [ ] AMP criteria met (link test cases)
- [ ] Unit / E2E tests added or updated
- [ ] Screenshots for UI changes
- [ ] No secrets in code or config

Linking code to work

  • Azure Repos: mention #1042 in a commit or PR to link it
  • Fixes #1042 in a commit can resolve the story (a repository setting)
  • GitHub repos connected to Boards: use AB#1042
  • Or link from the story’s Development section, or create the branch from the story

Turn on “complete linked work items after merging” so the board updates itself.

A PR template in the .azuredevops folder, or the repo root or docs folder, pre-fills every new PR description. Keep it short or people ignore it.

Linking: in Azure Repos you mention the work item with a hash and the ID. The AB-hash syntax is for GitHub repositories connected to Azure Boards; both are worth knowing as many teams use GitHub for code and Boards for work.

Creating the branch from the story's Development section links everything automatically, which is the simplest habit to teach.

Automation: CLI, REST and hooks

Automate everything unhuman: let the platform keep itself tidy.

Module 6, about 15 minutes: the az CLI, the REST API and how to authenticate safely, service hooks and Logic Apps, and pipelines at a glance.

Module 6 · CLI

Work items from the command line

boards.sh
# Create a story under a feature
ID=$(az boards work-item create --type "User Story" \
  --title "Add a new contact" --area "Delivery\Apps" \
  --iteration "Delivery\2026\Sprint 21" \
  --fields "Microsoft.VSTS.Scheduling.StoryPoints=3" \
  --query id -o tsv)

az boards work-item relation add --id $ID \
  --relation-type parent --target-id 1001

# Run WIQL and list the results
az boards query --wiql "SELECT [System.Id], [System.Title]
  FROM WorkItems WHERE [System.State] = 'Active'
  AND [System.AssignedTo] = @Me" -o table

# Open a PR linked to the story
az repos pr create --source-branch users/jo/1042-add-contact \
  --target-branch main --work-items $ID --auto-complete true
  • az devops — projects, teams, users, security
  • az boards — work items, areas, iterations, queries
  • az repos — repos, PRs, policies
  • az pipelines — runs, variables, environments
  • az devops invoke — any REST call the CLI lacks

Add -o json and --query (JMESPath) to script the output.

The azure-devops extension for the Azure CLI covers most daily tasks. Use it for bulk changes, setup scripts and for AI agents, which are very good at driving CLIs.

When something isn't covered, az devops invoke or az rest call the REST API using the same sign-in.

Module 6 · REST API

The REST API, without stored secrets

update-story.sh
# Entra token for Azure DevOps (fixed resource ID)
TOKEN=$(az account get-access-token \
  --resource 499b84ac-1321-427f-aa17-267ca6975798 \
  --query accessToken -o tsv)

URL="https://dev.azure.com/contoso/Delivery/_apis/wit/workitems/1042?api-version=7.1"

curl -X PATCH "$URL" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json-patch+json" \
  -d '[{ "op": "add",
        "path": "/fields/System.State",
        "value": "Active" }]'
AuthUse for
Entra ID user tokenScripts you run yourself
Managed identity / service principalLogic Apps, Functions, pipelines; add the identity as a user
Personal access tokenLast resort: narrow scope, short expiry, never in code

The REST API is versioned; pin api-version. Updates use JSON Patch with the json-patch content type.

For authentication, Microsoft is steering everyone towards Entra ID tokens and away from PATs. Services should use a managed identity or service principal added to the organisation, so there is no secret to leak or rotate. If you must use a PAT, scope it narrowly and give it a short expiry.

Module 6 · Event-driven automation

Service hooks and Logic Apps

Feature updatedEffort or MoSCoW changes
Service hookWeb Hook subscription
Logic AppManaged identity, no secrets
REST APIRecalculate the Epic, add a comment
  • Service hooks fire on events: work item created or updated, PR created or merged, build completed
  • Filter the subscription (type, area, field) to avoid noise
  • Real example: T-Minus-15’s effort-rollup Logic App recalculates an Epic’s effort from its Features (excluding Won’t Have)
  • Deployed with Bicep, system-assigned managed identity

Service hooks push events out of Azure DevOps. The Web Hooks target can call a Logic App HTTP trigger, an Azure Function or anything else.

The T-Minus-15 open-source project has a t-15-logicapps repo with real examples. effort-rollup keeps epic totals in sync with their features. It is deployed with Bicep and uses a managed identity, so no secret lives anywhere.

Watch for loops: an automation that updates a work item can trigger itself. Filter on the fields you care about.

Flight rules

Rules that speed you up

  • One project, many teams — areas for what, iterations for when
  • Inherit, don’t fork the process; change it centrally
  • No story without AMP criteria before it enters a sprint
  • WIP limits on every board; talk about red columns at stand-up
  • Protect main: reviewers, linked work, build validation
  • Every PR linked to a work item; branches from the story
  • Shared queries and dashboards instead of status reports
  • No PATs in code: Entra tokens and managed identities

These eight rules are the takeaway. If the team only adopts these, Azure DevOps will be a reliable source of truth.
