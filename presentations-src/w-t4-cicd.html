Why it matters

Measure delivery, not effort

The DORA research measures software delivery with four key metrics. Good CI/CD moves all four at once.

ThroughputDeployment frequency

How often you release to production.

ThroughputLead time for changes

Commit to running in production.

StabilityChange failure rate

Share of releases that need a fix or rollback.

StabilityTime to restore

How quickly you recover from a failed change.

Speed and stability are not a trade-off. Teams that deploy small changes often also fail less and recover faster.

These are the four keys from the DORA research programme behind the State of DevOps reports. Recent reports add a fifth measure, rework rate, but these four are the classic starting point.

The key message: automation lets you go faster and safer at the same time, because each change is small and goes through the same checks every time.

Ask the room: how long does a one-line fix take to reach production today?

01

Continuous integration

Every change built, tested and checked before it reaches main.

Continuous integration means merging small changes to main often, with an automated build proving each one works.

If a build is red, fixing it is the team's top priority.

Module 1 · Continuous integration

Triggers and pull request validation

azure-pipelines.yml
name: 1.4.$(Rev:r)          # run number = version

trigger:
  batch: true                 # queue one run, not many
  branches:
    include: [ main, release/* ]
  paths:
    exclude: [ docs/*, '*.md' ]

pr: none   # Azure Repos: PR runs come from a branch policy

Branch policy on main

  • Build validation: the pipeline must pass
  • Reviewers: at least one, not the author
  • Linked work item and resolved comments
  • Squash merge for a clean history

The YAML pr: trigger only applies to GitHub and Bitbucket repos.

CI triggers fire on pushes to the listed branches; path filters stop documentation changes from triggering builds.

For Azure Repos Git, pull request validation is configured as a build validation branch policy, not with the pr keyword. For GitHub repos you use the pr trigger instead.

The name line sets the run number, which we reuse as the build version.

Module 1 · Continuous integration

A fast, trustworthy CI job

Build stage · steps
variables:
  npm_config_cache: $(Pipeline.Workspace)/.npm

steps:
  - task: Cache@2
    inputs:
      key: 'npm | "$(Agent.OS)" | package-lock.json'
      path: $(npm_config_cache)
  - script: npm ci
  - script: npm run lint && npm test -- --coverage
  - task: PublishTestResults@2
    inputs: { testResultsFiles: '**/junit.xml' }
  - task: PublishCodeCoverageResults@2
    inputs: { summaryFileLocation: 'coverage/cobertura-coverage.xml' }
  - script: npm run build
  - publish: dist          # pipeline artifact, built once
    artifact: web

Keep it under 10 minutes

  • Cache dependencies keyed on the lock file
  • Fail fast: lint and unit tests first
  • Publish results so failures show in the PR
  • Static analysis (e.g. SonarQube, CodeQL) as a gate
  • Dependency scanning for vulnerable packages

Walk through the steps top to bottom. The cache key changes when the lock file changes, so restores stay correct.

Publishing test and coverage results gives reviewers a Tests and Code Coverage tab on the run and on the pull request.

A slow CI pipeline is a pipeline people work around. Aim for feedback in under ten minutes.

Module 1 · Continuous integration

Build once, promote everywhere

Artifact 1.4.27Built and tested once
Testconfig from test settings
Pre-productionconfig from pre-prod settings
Productionconfig from prod settings

Do

  • Keep environment config outside the artifact
  • Version every build: MAJOR.MINOR.PATCH + run number
  • Tag the commit that produced a release

Pitfall: rebuilding per environment. What you tested is no longer what you ship — a different package, different dependencies, different bugs.

The most important CI rule: one build, one artifact, promoted through every environment.

Environment differences belong in configuration: app settings, Key Vault references, Bicep parameter files and Power Platform deployment settings.

Semantic versioning tells consumers what changed; the run number makes every build traceable.

Live demo

A pull request that proves itself

  1. Add a build validation policy to mainDirect pushes to main are now blocked
  2. Open a PR with a failing unit testValidation fails; the test shows on the PR’s Tests tab
  3. Fix the test and push againValidation re-runs and passes; the cache restore is quick
  4. Complete the PR with squash mergeCI on main publishes artifact web with a new version

Demo in the sample project. Show the branch policy screen, then the failed PR run and its Tests tab.

Point out the second run is faster because of the cache hit. Finish on the artifact and run number on main.

YAML pipelines in depth

Pipelines as code: versioned, reviewed and reused like everything else.

Now we go deeper into YAML: the structure, how to reuse it with templates and how to govern it across many teams.

Module 2 · YAML pipelines

Stages, jobs, steps — and how they run

  • Pipelineone YAML file
  • StageBuild, DeployTest, DeployProd
  • Jobruns on one agent
  • Stepscript or task
  • Stages run in sequence by default
  • Jobs in a stage run in parallel
  • dependsOn and condition change the order
Ordering and conditions
stages:
  - stage: Build
    jobs:
      - job: build
        strategy:
          matrix:                 # same job, two OSes
            linux:   { vmImage: ubuntu-latest }
            windows: { vmImage: windows-latest }
        pool: { vmImage: $(vmImage) }

  - stage: DeployTest
    dependsOn: Build

  - stage: DeployProd
    dependsOn: DeployTest
    condition: |
      and(succeeded(),
          eq(variables['Build.SourceBranch'], 'refs/heads/main'))

A pipeline is a tree. Stages group jobs, jobs get an agent, steps run on that agent.

The matrix runs the same job on two operating systems in parallel. The condition makes sure only builds from main can ever reach production, even if someone queues a feature branch.

Module 2 · YAML pipelines

Templates: write it once

templates/node-build.yml
parameters:
  - name: nodeVersion
    type: string
    default: '22.x'
  - name: runTests
    type: boolean
    default: true

steps:
  - task: UseNode@1
    inputs: { version: ${{ parameters.nodeVersion }} }
  - script: npm ci
  - ${{ if parameters.runTests }}:
    - script: npm test
azure-pipelines.yml
steps:
  - template: templates/node-build.yml
    parameters:
      nodeVersion: '22.x'
      runTests: true
  • Step, job, stage and variable templates
  • Typed parameters catch mistakes when the run is created
  • Share across repos with resources: repositories, pinned to a tag

Templates are how you stop copy-pasting YAML between repositories. A template takes typed parameters and expands into steps, jobs or stages.

The if expression is evaluated when the pipeline is compiled, so a disabled step disappears from the run entirely.

Keep shared templates in their own repo and pin consumers to a tag so a template change can't break every pipeline at once.

Module 2 · YAML pipelines

Extends templates for governance

azure-pipelines.yml (in the app repo)
resources:
  repositories:
    - repository: templates
      type: git
      name: Platform/pipeline-templates
      ref: refs/tags/v3

extends:
  template: secure-pipeline.yml@templates
  parameters:
    buildSteps:
      - script: npm ci && npm test

The platform team owns the outer pipeline. App teams only fill in the gaps.

  • The template adds scanning, signing and approved agents
  • It can reject risky steps passed in

Add a Required template check on production environments and service connections: only pipelines that extend it can deploy.

Includes let you reuse pieces; extends lets a central template wrap the whole pipeline. That's the difference between convenience and governance.

Combined with the required template check, production can only be reached through the approved, scanned path. App teams still own their build steps.

Decision

Parameters vs variables

Template expressionMacroRuntime expression
Syntax${{ parameters.env }}$(appName)$[ variables.ver ]
EvaluatedWhen the run is compiledJust before each task runsAt run time, for variables and conditions
TypedYes — string, boolean, object…No — always stringsNo
Can shape the pipelineYes — loops, ifs, whole stagesNoConditions only
Use it forStructure and choices at queue timeValues passed to tasksValues from earlier jobs or stages

Pitfall: a variable set by a script (##vso[task.setvariable]) doesn’t exist when ${{ }} is evaluated — use $[ ] or an output variable.

This trips up almost everyone. The three syntaxes are evaluated at different times.

Rule of thumb: parameters for anything that changes the shape of the pipeline, macros for values, runtime expressions when you need a value produced earlier in the same run.

03

Environments, approvals and release

Make every release safe, visible and boring.

Delivery is the other half of CI/CD. We look at deployment jobs, environments, checks and how to release without downtime.

Module 3 · Release

Deployment jobs and environments

DeployProd stage
- stage: DeployProd
  jobs:
    - deployment: web
      environment: app-prod       # checks live here
      strategy:
        runOnce:
          deploy:
            steps:          # artifacts download automatically
              - task: AzureWebApp@1
                inputs:
                  azureSubscription: sc-app-prod
                  appName: app-sample-prod
                  deployToSlotOrASE: true
                  resourceGroupName: rg-app-prod
                  slotName: staging
                  package: $(Pipeline.Workspace)/web

An environment gives you

  • Deployment history: which run, commit and work items went where
  • Checks that run before any job targets it
  • Security: which pipelines may use it
StrategyUse for
runOnceMost apps: deploy all at once
rollingVM targets, in batches
canarySmall slice of traffic first

A deployment job targets an environment. That single line is what connects your YAML to approvals, checks and deployment history.

runOnce is what most PaaS apps need. Rolling and canary work with environment resources such as virtual machines and Kubernetes; for App Service we usually get the same safety from deployment slots.

Module 3 · Release

Approvals and checks

People
  • Approvals by a person or group
  • Block self-approval by the person who queued the run
  • Set a timeout
Policy
  • Branch control: only main or release/*
  • Required template
  • Business hours
  • Exclusive lock: one deployment at a time
Signals
  • Query Azure Monitor alerts
  • Invoke REST API or Azure Function, e.g. change ticket status
  • Evaluate artifact policies

Checks belong to the environment, not the YAML — so nobody can remove them in a pull request.

Checks are configured on the protected resource: the environment, service connection, agent pool or variable group.

Because they are not in the YAML, a developer can't bypass them by editing the pipeline. That's why production approvals should always live here.

Automated checks such as alerts and change tickets let you remove manual steps over time.

Module 3 · Release

Zero downtime with deployment slots

DeployNew version to the staging slot
Warm up and verifySmoke tests against the staging URL
SwapStaging becomes production
Roll back?Swap again: seconds, not hours
Swap step
- task: AzureAppServiceManage@0
  inputs:
    azureSubscription: sc-app-prod
    Action: 'Swap Slots'
    WebAppName: app-sample-prod
    ResourceGroupName: rg-app-prod
    SourceSlot: staging

Mark environment-specific settings as slot settings, or they swap with the code.

Database changes must be backwards compatible — both versions run against the same schema during a swap.

Blue-green on App Service: deploy to a staging slot, check it, then swap. The swap warms the instances first, so users see no downtime.

Rolling back is another swap. The catch is data: use expand-and-contract migrations so old and new code both work with the schema.

Module 3 · Release

Release Flow: branching that fits CI/CD

Topic branchShort-lived: hours to days
PR into mainAlways releasable
release/2026.11Cut per sprint
DeployFrom the release branch
  • One long-lived branch: main
  • Release branches are never merged back
  • Hotfixes go to main first, then cherry-pick to the release branch

Unfinished work ships behind feature flags, not on long-running branches.

Release Flow is the trunk-based model Microsoft uses for Azure DevOps itself. It avoids the merge pain of GitFlow.

Fix forward on main first so the fix is never lost, then cherry-pick it into the current release branch. The W-M6 Operate workshop covers branching strategies in more depth.

04

Secrets and identity

The best secret is the one that doesn’t exist.

Pipelines hold the keys to production, so they're a prime target. This module is about removing stored credentials altogether.

Module 4 · Identity

Service connections without secrets

Pipeline jobUses service connection sc-app-test
Short-lived tokenIssued by Azure DevOps for this job (OIDC)
Microsoft Entra IDFederated credential trusts that issuer and subject
AzureAccess token, scoped by RBAC
  • Workload identity federation: no client secret to store, leak or rotate
  • Backed by an app registration or a user-assigned managed identity
  • Subject is tied to the connection: sc://org/project/connection

Least privilege: one connection per environment, scoped to its resource group, with a role such as Contributor — not Owner on the subscription.

Workload identity federation replaces stored client secrets. The job gets a short-lived token from Azure DevOps, and Entra ID exchanges it for an Azure access token because a federated credential trusts that exact connection.

Existing secret-based connections can be converted in place. Separate connections per environment mean a test pipeline can never touch production.

Module 4 · Secrets

When you need a secret, get it from Key Vault

Option 1 · task
- task: AzureKeyVault@2
  inputs:
    azureSubscription: sc-app-test
    KeyVaultName: kv-sample-test
    SecretsFilter: 'ApiKey,SqlPassword'
- script: ./smoke-test.sh
  env:
    API_KEY: $(ApiKey)      # secrets must be mapped explicitly
Option 2 · variable group linked to Key Vault
variables:
  - group: app-test-secrets

Better still

  • Apps use managed identity and Key Vault references — the pipeline never sees the secret
  • Secret variables are masked in logs and not passed to scripts unless mapped

Never echo secrets or write them to artifacts. Masking can’t catch transformed values.

Two ways to pull secrets into a pipeline: the Key Vault task, or a Library variable group linked to a vault. Both use the federated service connection.

The best design is for the app itself to read Key Vault with its managed identity, so secrets never pass through the pipeline at all.

Live demo

Create a federated service connection

  1. Project settings → Service connections → Azure Resource ManagerWorkload identity federation is the recommended option
  2. Scope it to rg-app-test and name it sc-app-testAn identity is created with a federated credential
  3. Open the identity in Entra IDNo client secrets; issuer and subject on the federated credential
  4. Run az group show through AzureCLI@2Works; the same call against another resource group is denied

Create the connection live. Show the empty Certificates and secrets blade on the identity: there is nothing to leak.

Then prove least privilege by trying a resource group the identity has no role on.

05

Infrastructure-as-code

Environments you can rebuild from Git in minutes.

If an environment can only be rebuilt from memory and portal clicks, it isn't really under control. We use Bicep for Azure.

Module 5 · Infrastructure-as-code

Bicep: one template, every environment

infra/main.bicep
targetScope = 'resourceGroup'

@allowed([ 'test', 'prod' ])
param env string

module plan 'modules/plan.bicep' = {
  params: {
    name: 'asp-sample-${env}'
    sku: env == 'prod' ? 'P1v3' : 'B1'
  }
}

module web 'modules/webapp.bicep' = {
  params: {
    name: 'app-sample-${env}'
    planId: plan.outputs.id   // wires modules together
  }
}
infra/test.bicepparam
using 'main.bicep'
param env = 'test'
  • Modules for reuse; share them through a Bicep registry
  • One parameter file per environment
  • Outputs wire modules together — no hard-coded IDs
  • Lint with az bicep build in CI

Same template, different parameter file per environment. The SKU expression shows how to keep test cheap without a second template.

Bicep compiles to ARM, so anything Azure supports, Bicep supports on day one.

Module 5 · Infrastructure-as-code

Preview, then deploy, from the pipeline

DeployTest stage · infrastructure
- task: AzureCLI@2
  displayName: Bicep what-if, then deploy
  inputs:
    azureSubscription: sc-app-test   # federated
    scriptType: bash
    scriptLocation: inlineScript
    inlineScript: |
      az deployment group what-if \
        --resource-group rg-app-test \
        --parameters infra/test.bicepparam

      az deployment group create \
        --name infra-$(Build.BuildId) \
        --resource-group rg-app-test \
        --parameters infra/test.bicepparam

What-if

Shows what will be created, changed or deleted — before anything happens.

  • Run it in the PR build so reviewers see the impact
  • For production, put an approval between what-if and deploy
  • Infrastructure deploys before the app in each stage

Two steps: what-if previews the change, create applies it. Both run as the federated service connection.

Naming the deployment after the build ID gives you a deployment history in the resource group that maps back to the pipeline run.

Decision

Drift, and choosing a tool

Stopping drift

  • Read-only portal access in test and production
  • Deployment stacks to manage resource lifecycle and deny manual changes
  • Scheduled what-if runs to spot changes
  • Azure Policy for guardrails such as regions, SKUs and tags
BicepTerraform
CloudsAzure onlyMulti-cloud and SaaS providers
State fileNone — Azure is the stateMust store and lock it
New Azure featuresDay oneWhen the provider adds them
Preview changeswhat-ifplan
Best forAzure-centric teamsMixed estates

Drift happens when someone fixes production in the portal. The next deployment either undoes the fix or fails.

Both Bicep and Terraform are good choices. For an Azure-only estate, Bicep has less to manage because there's no state file.

Deploying Power Platform solutions

Low-code deserves the same pipeline discipline as code.

Power Platform solutions can and should go through the same source control, review and release process as everything else.

Module 6 · Power Platform

Solutions through source control

Dev environmentMakers build in an unmanaged solution
ExportUnmanaged .zip
UnpackReadable XML and files
Commit + PRReviewed diff
Pack managedBuilt from Git
ImportTest, then prod, with settings
  • Git is the source of truth, not the dev environment
  • Managed solutions only beyond dev
  • Bump the solution version on every build

Pitfall: importing unmanaged solutions into test or production. You can’t cleanly remove or upgrade them later.

Export from dev, unpack into source files, review them in a pull request, then build a managed solution from Git and import it downstream.

Run the Power Apps solution checker in the build to catch problems early. The W-T3 Power Platform workshop covers solutions and environments in more depth.

Module 6 · Power Platform

Power Platform Build Tools in YAML

Export pipeline (from dev)
- task: PowerPlatformToolInstaller@2
- task: PowerPlatformExportSolution@2
  inputs:
    authenticationType: PowerPlatformSPN
    PowerPlatformSPN: sc-pp-dev
    SolutionName: SampleApp
    SolutionOutputFile: out/SampleApp.zip
    Managed: false
- task: PowerPlatformUnpackSolution@2
  inputs:
    SolutionInputFile: out/SampleApp.zip
    SolutionTargetFolder: solutions/SampleApp
# then commit to a branch and open a PR
Release pipeline (from Git)
- task: PowerPlatformToolInstaller@2
- task: PowerPlatformPackSolution@2
  inputs:
    SolutionSourceFolder: solutions/SampleApp
    SolutionOutputFile: out/SampleApp_managed.zip
    SolutionType: Managed
- task: PowerPlatformImportSolution@2
  inputs:
    authenticationType: PowerPlatformSPN
    PowerPlatformSPN: sc-pp-test
    SolutionInputFile: out/SampleApp_managed.zip
    UseDeploymentSettingsFile: true
    DeploymentSettingsFile: config/test.settings.json
    AsyncOperation: true

Same steps by hand with the pac CLI: pac solution export, unpack, pack, import. Use it locally, and in GitHub Actions.

Two pipelines: one exports and unpacks from dev into a pull request; the other packs a managed solution from Git and imports it, one stage per environment.

The service connections authenticate as an application user in each environment. Check the current task versions in the Marketplace before the lab; these are the v2 tasks.

Module 6 · Power Platform

One solution, per-environment settings

config/test.settings.json
{
  "EnvironmentVariables": [
    { "SchemaName": "sample_ApiBaseUrl",
      "Value": "https://api-test.example.org" }
  ],
  "ConnectionReferences": [
    { "LogicalName": "sample_sharedoffice365_ref",
      "ConnectionId": "<connection id in test>",

}
Generate the template
pac solution create-settings \
  --solution-zip SampleApp.zip \
  --settings-file test.settings.json
  • Environment variables for URLs, IDs and flags
  • Connection references bound to connections owned by a service account
  • No manual fix-ups after import

Environment variables and connection references are the Power Platform version of environment config. The deployment settings file sets them during import.

Create the connections in each target environment once, owned by a service account, and record their IDs in the settings file. Keep secret values in Key Vault-backed environment variables, not in this file.

Decision

Build Tools or Pipelines in Power Platform?

Pipelines in Power PlatformAzure DevOps + Build Tools
Set up byMakers and admins, in the maker portalDevelopers and DevOps engineers, in YAML
Source controlOptional, via Git integrationBuilt in: unpacked solution in Git
Pull request reviewNoYes
Mixed releases (code + Azure + solution)NoYes, in one pipeline
Best forCitizen-developer apps, simple promotionProfessional teams and critical solutions

They can coexist: makers self-serve low-risk apps; important solutions go through the full pipeline.

Pipelines in Power Platform is the in-product option and is great for getting makers off manual exports. It's quick to adopt but has less control.

When a solution matters, or when it ships alongside Azure resources and custom code, use Azure DevOps with Build Tools so everything is reviewed and released together.

Flight rules

Rules that speed you up

  • Everything as code — pipelines, infrastructure and solutions in Git
  • Every change through a PR with build validation
  • Build once, promote the same artifact everywhere
  • No stored secrets — federated identity and Key Vault
  • Checks on environments, not in the YAML
  • Humans approve production; automation does the rest
  • What-if before you change infrastructure
  • Managed solutions only beyond dev
  • Templates for the boring bits, extends for governance
  • Make rollback boring — slots and previous artifacts

If you remember one slide, make it this one. Each rule removes a whole category of release-day problems.

Suggest teams turn these into a Definition of Done item for any new pipeline.
