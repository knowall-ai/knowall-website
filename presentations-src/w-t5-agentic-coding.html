Why it matters · Module 1

From autocomplete to agents

GoalA task with clear acceptance criteria
PlanRead the code, propose an approach
ActUse tools: edit files, run commands
ObserveRead test output, errors, diffs
Human reviewApprove, redirect or reject

Plan → act → observe repeats until the goal is met, or the agent stops and asks.

The shift: the unit of work moves from a line of code to a task. Agents shine where the goal is clear and the result can be checked: features with tests, refactoring, upgrades, explaining code.

The catch: an agent can be confidently wrong, fast. Vague goals, no tests or regulated logic without human sign-off just produce rework.

Most teams have used autocomplete and chat. Agents are different because they act: they read files, run commands and check their own work in a loop. Tests and builds are the agent’s eyes, so a task it can’t verify is a task it can’t do well.

Point out the human review step: it is not optional. The agent proposes, people decide what ships. Ask the room who has already used an agent on a real codebase, and what surprised them.

Module 2 · Claude Code in practice

Commands, project memory and permissions

Everyday commands
  • claude for a session, claude -p for scripts
  • /init drafts a CLAUDE.md
  • /clear for each new task, /context to see what is loaded
  • Also in VS Code, JetBrains, the desktop app and the web
CLAUDE.md
  • The onboarding doc for agents, loaded every session
  • Commands, architecture and rules
  • Committed and reviewed like code
  • Short and specific beats an essay
Permissions
  • Modes from plan (read only) to acceptEdits
  • Allow, ask and deny rules in .claude/settings.json
  • deny wins; real isolation comes from containers or VMs

Habit: start in plan mode, read the plan, then switch to acceptEdits to execute. Shift+Tab cycles modes.

Keep this slide short and show everything live in the next demo. The ideas — project memory, planning, permissions — apply to any coding agent; we use Claude Code because it is what we use day to day.

Permission mode names change between versions, so check claude --help on the demo machine beforehand. Plan mode is the single biggest quality lever: reviewing a plan takes a minute, reviewing a wrong implementation takes an hour.

Live demo

From /init to a planned change

  1. Open the sample repo and run /initA draft CLAUDE.md with commands and structure
  2. Edit it: add rules such as tests required, no .env access, sample data onlyShort, specific, committed on a branch
  3. Add allow and deny rules to .claude/settings.jsonSafe commands run without prompts; .env reads are refused
  4. Switch to plan mode and ask for a small featureA written plan, no files changed
  5. Challenge one step of the plan, then approve itAgent adjusts the plan, then implements with tests

Keep the feature small, such as adding a filter to a list endpoint. The point is the workflow, not the feature. Deliberately push back on part of the plan to show that steering early is cheap.

Prep: a sample repo with a working test command, a ready-made settings.json to paste, and a recording or screenshots as a fallback in case the network misbehaves.

Module 3 · Skills and specialist agents

Skills, subagents and plugins

SkillSubagentPlugin
What it isInstructions and files for one kind of taskA specialist with its own prompt, tools and contextA bundle of skills, agents, hooks and MCP servers
Where it lives.claude/skills/<name>/SKILL.md.claude/agents/<name>.mdA marketplace or Git repo
How it runsLoaded when relevant, or /nameDelegated to; works in a separate contextInstalled with /plugin
Use it for“How we create a PR”“A tester who reviews coverage”Sharing the lot across teams

Worked example: the T-Minus-15 plugin gives each lifecycle stage an agent — planner, prepper, designer, engineer, tester, operator — plus reviewers for architecture, performance and security.

A simple way to remember it: a skill is a recipe, a subagent is a colleague, and a plugin is how you share both. Subagents also manage context: a big search runs in the subagent’s context and only the summary comes back.

The lesson for the team: map agents to your process, not the other way round. Start with one or two, such as a story writer and a reviewer.

Live demo

A skill and a specialist at work

  1. Install the plugin with /plugin and list what it addsNew skills and agents appear in /agents and the skill list
  2. Create .claude/skills/create-pr/SKILL.md with the team’s PR checklistThe skill appears when you ask “what skills do you have?”
  3. Ask for a user story for a small screenThe user-story skill drafts a story with AMP criteria
  4. Run the read-only reviewer agent on the branchRanked findings with file:line references

Show how a skill is picked up from its description without naming it, then show it invoked explicitly with a slash command. The create-pr skill gets used again in the last demo.

When the reviewer reports findings, decide out loud which to accept. That human judgement is the point. Prep: install the plugin once beforehand so the download doesn’t eat demo time.

Module 4 · Specs and prompts

Agents build exactly what you ask for

User story 1234 · Filter orders by status
Acceptance (A)
SCENARIO: Filter the order list by status
GIVEN 20 sample orders, 5 with status "Shipped"
WHEN  the user selects "Shipped" in the status filter
THEN  exactly 5 orders are listed

Measure (M)
- List updates within 500 ms for 1,000 orders

Proof (P)
- TC1: Playwright test orders-filter.spec.ts

A prompt an agent can execute

  • Goal: the story and its AMP criteria
  • Context: files and patterns to follow
  • Constraints: what not to change
  • Done when: named tests pass, lint is clean

One story per session. Plan first. Two failed corrections? /clear and sharpen the spec.

Welcome back from the break. This is the highest-value skill of the day. AMP is the T-Minus-15 format for acceptance criteria: Acceptance in Gherkin the agent can turn into tests, Measure with numbers so “fast” isn’t opinion, and Proof naming the tests that show it’s done.

Where requirements are vague, the right move is not a better prompt but a better story. Every correction you make twice belongs in CLAUDE.md or a skill.

Live demo

From story to tested code

  1. Try a vague prompt in plan mode: “Add filtering to the orders page and make it fast”A plan full of guesses, with nothing to check it against
  2. /clear, then give story 1234 with its criteria, context and constraintsA plan that names the files and the tests it will write
  3. Ask for the failing tests first, and review themTests fail for the right reason
  4. Switch to acceptEdits and let it implementTests pass; lint and typecheck clean

The contrast between the two prompts is the lesson, so let the room see the vague plan before clearing it. Ask them what is missing before you show the good prompt.

Prep: the story and the executable prompt saved in a text file to paste, and the repo’s test command checked on the demo machine.

Module 5 · Tools and integration

MCP, hooks and headless mode

MCP servers
  • An open standard for plugging in external tools
  • Azure DevOps, GitHub, Playwright and more
  • Shared with the team in .mcp.json
Hooks
  • Shell commands on events such as PreToolUse and PostToolUse
  • Exit code 2 blocks the action
  • Enforcement, where CLAUDE.md is guidance
Headless and CI
  • claude -p as a pipeline step
  • Strict allow list and a budget cap per run
  • Advisory first: post findings, don’t gate merges

Each MCP server is code with your credentials, and anything the agent reads can carry prompt injection. Trusted servers only, least privilege.

This module widens the agent’s reach beyond the repo. If something must always happen, such as formatting or blocking pushes to main, make it a hook rather than an instruction.

For CI, start with agent review as advice to a human reviewer. Only consider gating on it once you trust its signal on your codebase. The CLI evolves quickly, so check flags against claude --help.

Live demo

The agent drives a browser

  1. Start the sample app locallyThe orders page on localhost
  2. Ask the agent to use Playwright MCP to check story 1234’s criteriaIt opens the page, filters, and reports what it sees
  3. Ask it to turn the walkthrough into orders-filter.spec.tsA Playwright test mapped to TC1
  4. Edit a file and watch the formatting hook runPrettier runs after every edit, no prompt needed
  5. Run a review headless with claude -p and a strict allow listFindings as JSON, as a pipeline step would produce

This is often the moment the room gets it: the agent can see the running app, not just the code. Point out that the test it writes is ordinary Playwright code, reviewed and committed like any other.

Prep: the Playwright MCP server and the formatting hook configured beforehand, and the app already running in a second terminal.

Module 6 · Quality and guardrails

Every change, the same path

StoryAMP criteria
BranchAgent builds with tests
Agent reviewReviewer and security checks
CIBuild, tests, scans
Human reviewApproves the PR
MergeBranch policy enforced
Guardrails
  • Deny rules and hooks for secrets and risky commands
  • Least-privilege tools and MCP servers
  • Budget caps in CI
Governance
  • Sample data only unless approved
  • Agreed data-use terms and a short AI use policy
  • A named human accountable for every merge

Watch the tests: an agent may “fix” a failing test by weakening it. Review test changes as closely as code.

The principle is simple: no special treatment. Agent-authored changes go through the same branch policies, required reviewers and CI as human code, and meet the same Definition of Done.

For regulated organisations, governance is what unlocks adoption. Check provider terms and your information governance team’s requirements; this is a starting checklist, not legal advice.

Live demo

Review, pull request and merge

  1. Ask the agent to push straight to mainA PreToolUse hook blocks it and says why
  2. Run the reviewer agent on the story 1234 branchFindings ranked by severity; fix or justify each one
  3. Check the diff for test changes the story didn’t ask forNo weakened tests, no unrequested changes
  4. Ask the agent to open the PR using the create-pr skillA PR with what, why and how tested
  5. A second person reviews, approves and mergesA merged PR, approved by a human who didn’t write it

This closes the loop: the story from Module 4 ends as a merged pull request through the same path as any human change. Make the human approval visible; it is the step that makes agent work trustworthy.

Prep: the blocking hook script in place, a branch policy on main in the demo repo, and a second person or account ready to approve.

Recap

Flight rules, and where next

Flight rules
  • People are accountable — a human approves every merge
  • Spec before code — AMP criteria, then plan mode
  • Tests are the agent’s eyes — no tests, no agent
  • Memory as code — CLAUDE.md, skills and settings in Git
  • Enforce with hooks, least privilege everywhere
  • Small stories, sample data only
Optional deep dives
  • Building a skill and agent library for your team
  • MCP for Azure DevOps and internal systems
  • Agents in CI/CD: review, triage and release notes
  • Governance and an AI use policy for engineering
